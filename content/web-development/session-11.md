# Publishing Your Site with GitHub Pages

## A. Session Identification
<!-- kind:identification -->
**Week / module:** Week 4 — Module 4: Polish and Deploy

**Recommended duration:** 105 minutes

**Difficulty:** Beginner (first contact with Git and GitHub)

**Prerequisite knowledge:** Sessions 1–10. The learner must have a working multi-page site (or at least a working index.html with linked css/style.css and js/app.js ), know the Chrome DevTools Console, understand relative file paths, and be able to run the site locally (double-click or Live Server).

**Connection to previous work:** In Session 10 the learner fixed bugs and optimised the site, but it still lived only on one computer. This session puts it on the internet so anyone — a customer, a relative, a future employer — can open it with a real link.

**Preparation before class:** Academy PCs on and logged in; Google Chrome and VS Code installed; internet access is required this session (unlike most earlier sessions); each learner's CEA-WebDev-Name project folder ready; instructor GitHub account already created for the demo; a phone with mobile data for the "test on a phone" step; the projector able to show the instructor's GitHub browser tab.

## B. Learning Outcomes
<!-- kind:outcomes -->
By the end of this session, the learner will be able to:
1. Explain in their own words what Git is and what GitHub is, and state the difference between the two without confusing
them.
2. Create a free GitHub account (or log in to an existing one) with a verified email address.
3. Create a public repository on GitHub and upload a website's files using the web interface.
4. Enable GitHub Pages for a repository and locate the published URL ( https://username.github.io/repo-name/ ).
5. Describe the structure of the published URL and explain how to update the live site after editing a file.
6. Write a simple README.md containing a project name, description, feature list, how to run the site, and the author's name.
7. Test a live site on both a desktop browser and a mobile phone, and confirm that assets (CSS, JavaScript, images) load.
8. Diagnose and fix the four common deployment problems: Pages set to the wrong branch/folder, a 404 error, a case-
sensitive file name ( index.html vs Index.html ), and assets missing because of wrong relative paths.
9. Use the Git command line (for learners who are ready) to init , add , commit , add a remote and push a project to
GitHub.

## D. OPENING ACTIVITY (6 minutes)
<!-- kind:opening -->
Instructor setup: On the projector, open two browser tabs side by side. In the left tab, open the learner-style local file
file:///C:/Users/.../CEA-WebDev-Name/index.html . In the right tab, open a real, already-published site (for example the instructor's
own demonstration page at https://<instructor-username>.github.io/demo-deploy/ ).
What the instructor says:
"Look at the left tab. This is the site we have been building for four weeks. It works — but look at the address bar: it starts
with file:///C:/Users/... . That address only works on this one computer. If I send it to your phone right now, it will not
open. If I paste it in a WhatsApp message to a customer, they will see nothing.
Now look at the right tab. This address starts with https:// . I can send this link to anybody in the world — your customer
in Aba, your aunt in Lagos, a recruiter in Abuja — and they open it on any phone or computer. Nothing to install.
So the question for today is simple: how do we move our site from the left tab to the right tab? How do we get a real link?"
Expected learner response: Learners often say "you need to pay for a website" or "you need to buy a domain." Accept the
answers, then correct the biggest myth:
"You do not need to pay to get a real link. Today you will each publish a working site to the internet, for free, using a
service called GitHub Pages. By the end of this session, every one of you will have a link you can send to anyone."
Why this opener works: It shows the exact gap (a private file versus a public link) with two visible tabs, kills the "it costs money"
fear, and promises a concrete reward — a link — that every learner wants before the session is over.

## E. PREREQUISITE REVIEW (7 minutes)
<!-- kind:prereq_review -->
Run this as a fast oral round-robin. Put the questions on the projector.
Question 1: "In your project folder, what is the special file name that a website's home page must have?"
Expected answer: index.html .
Common gap: learners call it home.html or Home.html . Correct firmly: for GitHub Pages, the home page file at the top level
Question 2: "Your CSS is in a folder called css . Write the line that links your stylesheet from index.html ."
Expected answer: <link rel="stylesheet" href="css/style.css"> .
Common gap: writing an absolute path like C:\Users\...\css\style.css . Remind them: website files always use relative
paths (paths relative to the current file), never Windows drive paths.
Question 3: "Your site uses fetch('data/products.json') . Why did we need Live Server for that in Session 7, and will it work on a
published site?"
Expected answer: fetch does not work from file:// because of browser security (CORS); it needs a server. On a published
GitHub Pages site, the site is served from a web server over https , so fetch works correctly.
Common gap: learners think the published site will have the same problem. Reassure them: publishing fixes the fetch
problem.
Question 4: "Name two things that must be in the same folder for your index.html to work normally."
Expected answer: the css folder and the js folder (and any images or data folders, and any other .html pages like
about.html , contact.html ).
Common gap: learners forget sub-pages. Remind them: all pages and folders must be uploaded, not only index.html .
Bridge to today (say this):
"You now have a complete site. It has structure, styling, behaviour, a cart that remembers, and a validated form. The only
thing missing is an audience. Today we get the audience. We will learn two words first — Git and GitHub — and then we
will publish."
Gap handling: If more than a third of the class cannot answer Question 1 and Question 2, spend five extra minutes opening each
learner's project folder together and confirming that index.html exists at the top level and that the stylesheet link uses a relative
path, before starting Section F.

## F. Full Lecture Notes
<!-- kind:lecture -->
F.1 Why deploy at all
The idea. To deploy means to put your website on a computer that is always switched on and connected to the internet, so that
anybody with the link can open it. That always-on computer is called a web server.
Plain-English definition. Right now your site lives on your laptop. A laptop sleeps, runs out of battery, and is only reachable by
you. A deployed site lives on a server that never sleeps, so the whole world can reach it.
Why this matters to a business. Imagine Adaeze Fashion has a beautiful shop built in this course. It sits on Adaeze's laptop. A
customer in Warri asks for her website and she says "come and see it on my laptop." That is not a business — that is a hobby. A
real URL that anyone can open turns a practice exercise into a shop window. Adaeze can put the link in her WhatsApp status,
her Instagram bio and her business card. Orders can begin.
Real-life comparison. Think of a school play. The rehearsal happens in a closed hall — only the cast sees it (your local file://
site). The performance happens on a stage with an audience and tickets — anyone can come (your deployed site). Deployment
is the night of the performance.
Limitation to state honestly. GitHub Pages hosts static sites: HTML, CSS, JavaScript and files like JSON and images. It does not
run a backend (no database, no logins on a server, no taking real payments). Our site is fully static — the cart is stored in the
visitor's own browser with localStorage — so GitHub Pages is a perfect fit.
F.2 Git and GitHub — two different things
These two words confuse beginners more than almost anything else in web development, so we separate them clearly.
Git is a version control tool that runs on your own computer. It records a history of every change you make to your files. Each
saved snapshot is called a commit. Git lets you see what changed, when, and go back to an earlier version if you break
something.
GitHub is a website ( https://github.com ) that hosts Git projects online. When you upload your Git project to GitHub, other
people (or a machine like GitHub Pages) can see and use it.
Plain-English comparison. Git is the notebook that remembers every draft of your work — page 1, page 2, and so on. GitHub
is the library shelf where you place the finished notebook so the whole world can read it.
Another way to say it:
Git = the tool. It lives on your computer. It works offline.
GitHub = the website. It lives on the internet. It needs network access.
Important misconception. "Git and GitHub are the same thing." They are not. You can use Git with no internet and never touch
GitHub. You can use GitHub without ever learning Git commands by uploading through the website — and that is exactly the
first method we will learn today.
Definition of a repository. A repository (often shortened to repo) is a project folder that is tracked, either by Git or by GitHub.
When we say "create a repository," we mean "create an online folder on GitHub to hold your website's files."
F.3 Creating a free GitHub account
The whole course rule applies here: no paid tools. GitHub accounts are free. Follow these steps exactly.
1. Open Chrome and go to https://github.com .
2. Click the Sign up button at the top right.
3. Enter your email address. Use an address you can open right now, because GitHub will send a verification code. A Gmail
address is fine.
4. Create a password (at least 8 characters, mix letters and numbers).
5. Choose a username. This is important: your username becomes part of your public web address. Choose something
professional and simple, for example adaeze-fashion-ph or blessingokoro-dev . Avoid nicknames with numbers you will be
embarrassed by later. Usernames may contain letters, numbers and hyphens only.
6. Solve the puzzle / verify you are human, then click Create account.
7. GitHub emails you a code (usually 6 digits). Type it into the box on screen. This verifies the account.
8. If asked whether you want the free or paid plan, choose Free.
Expected screen: After verification you land on your GitHub home dashboard with a welcome message and a Create
repository button.
What the learner should see: Their chosen username in the top-right corner. Write that username on Worksheet 11.1 — it is
part of your live URL later.
Common gap: Learners pick a username they later dislike, or one that is already taken (GitHub shows "username is not
available"). If taken, add a hyphen and a short word, e.g. adaeze-fashion-ph2 . Usernames can be changed later in Settings, but it
is easier to choose well now.
F.4 Deployment Path A — the web upload method (best for beginners)
This method uses only the GitHub website. No commands, no installation. It is the method we recommend for this session.
Step 1 — Create the repository.
1. Log in to GitHub.
2. Click the + icon at the top right, then click New repository.
3. In Repository name, type a short, lowercase name with hyphens, e.g. adaeze-fashion .
4. In Description, type a short sentence: "My shop website for Adaeze Fashion."
5. Select Public. (GitHub Pages requires a Public repo on the free plan. A Private repo cannot serve Pages for free.)
6. Tick Add a README file. (We will edit it later.)
7. Click the green Create repository button.
Expected screen: You are taken to the new repository page. You can see the repo name at the top and a single file, README.md .
Step 2 — Upload the website files.
1. On the repository page, click the Add file button (near the top right), then choose Upload files.
2. A drop zone appears that says "Drag files here to add them to your repository."
3. Open your CEA-WebDev-Name folder in Windows Explorer. Select all your site files and folders — index.html , about.html ,
contact.html , the css folder, the js folder, the images folder and the data folder (with products.json ).
4. Drag them into the browser drop zone, or click choose your files and select them. Upload the folders too — modern
GitHub keeps the folder structure when you drag folders in.
5. Wait for the file list to appear. It should show each file with a green icon.
6. Scroll down to Commit changes. Leave the default message ("Add files via upload"). Click the green Commit changes
button.
Expected screen: A blue banner says "Uploaded..." and the repository page now lists all your files: index.html , css/ , js/ ,
images/ , data/ , etc.
Critical fact to say aloud: "The index.html file must be in the top level — directly in the repository, not inside another folder. If
your index.html is inside a folder called website , GitHub Pages will show a 404 page. The home page must sit at the root."
Step 3 — Enable GitHub Pages.
1. On the repository page, click the Settings tab (top row, with a small gear icon).
2. In the left sidebar, under the heading Code and automation, click Pages.
3. Under Build and deployment, find Source. It is a dropdown; choose Deploy from a branch.
4. Under Branch, choose main from the dropdown, and leave the folder dropdown as / (root). Click Save.
5. A notification appears: "GitHub Pages source saved." Now wait. GitHub needs 1 to 3 minutes to build your site the first
time.
Step 4 — Get and test the URL.
1. Refresh the Pages settings screen every minute. When it is ready, a green message appears: "Your site is live at
https://username.github.io/repo-name/".
2. Click that link, or copy it and paste it into a new tab.
3. Your site should appear exactly as it did on your laptop.
Expected screen: The live page with your heading, your styling, your images and a working cart. The address bar shows
https://username.github.io/adaeze-fashion/ .
Say to the class: "Congratulations — you are now published. Send that link to one person before you leave this room."
F.5 Deployment Path B — the Git command-line method (for learners who are ready)
This method is faster once you know it, and it is what professional developers use. It requires Git for Windows installed on your
machine. These are the exact commands, with what each one does.
Open a terminal in your project folder: in VS Code, open your project, then press Ctrl + ` (the backtick key) to open the
integrated terminal. Type the commands one at a time.
```text
# 1. Tell Git who you are (do this once per computer)
git config --global user.name "Blessing Okoro"
git config --global user.email "blessing@example.com"
```
```text
# 2. Start tracking this folder with Git
git init
```
```text
# 3. Stage all your files (tell Git which changes to save)
git add .
```
```text
# 4. Save a snapshot with a message
git commit -m "First version of my shop website"
```
```text
# 5. Name the main branch 'main' (GitHub's default)
git branch -M main
```
```text
# 6. Connect your local folder to the GitHub repository
git remote add origin https://github.com/blessingokoro-dev/adaeze-fashion.git
```
```text
# 7. Upload your files to GitHub
git push -u origin main
```
Line by line, in plain English:
git config --global user.name "..." — stores your name on every commit. Run once.
git config --global user.email "..." — stores your email. Use the same email as your GitHub account.
git init — creates a hidden .git folder that turns your project folder into a tracked repository.
git add . — the dot means "everything in this folder." Stage all files for the next commit.
git commit -m "..." — saves a labelled snapshot. The message should describe what changed.
git branch -M main — names the branch main (GitHub's default branch name).
git remote add origin <URL> — links your local folder to the online repository. Use the URL GitHub shows under the green
Code button (HTTPS tab). It ends with .git .
git push -u origin main — uploads your commits to GitHub.
First-time authentication: GitHub will ask you to sign in or, more likely, to authenticate with a browser pop-up. Follow the
pop-up and approve. Older tutorials mention typing a password — GitHub removed password authentication, so if it asks, use
the browser sign-in route.
How to recognise success: After git push , the terminal prints lines that end with main -> main and branch 'main' set up to
track ... . Refresh your GitHub repository page — your files are now there. Then enable Pages exactly as in Section F.4, Step 3.
Useful follow-up commands:
```text
git status        # what has changed since the last commit?
git log --oneline # a short list of your saved snapshots
git add .         # stage new changes
git commit -m "Updated the price of the ankara dress"
git push          # upload the new commit (no need for -u the second time)
```
Limitation: this path is optional. If a learner finds the command line stressful, Path A is completely acceptable and produces the
same public result.
F.6 The published URL — its structure and how to update the site
The structure of the URL. For a repository named something other than your username:
```text
https://username.github.io/repo-name/
        └── your GitHub username
                    └────────── the fixed GitHub Pages domain
                                 └── your repository name
```
So for username adaeze-fashion-ph and repository adaeze-fashion , the URL is:
```text
https://adaeze-fashion-ph.github.io/adaeze-fashion/
```
Special case: if you name a repository exactly username.github.io (for example adaeze-fashion-ph.github.io ), then the site is at
the shorter address https://adaeze-fashion-ph.github.io/ . We will not use this special case in this course; use a normal repo
name.
How to update the live site after editing a file.
Path A (web upload): go back to the repository, click Add file → Upload files, drag the edited file(s) in, and click Commit
changes. GitHub Pages rebuilds automatically, usually within a minute. Changes are not instant — refresh after a short wait,
and use a hard refresh ( Ctrl + F5 ) if you still see the old version.
Path B (Git): in your terminal run git add . , then git commit -m "describe the change" , then git push . The live site updates
within a minute.
Say this clearly: "Editing the file on your laptop does nothing to the live site until you upload or push. GitHub only shows what
you have sent it."
F.7 Testing the live site
After publishing, you must test like a real visitor would.
On a desktop:
1. Open the live URL in Chrome.
2. Click through every page: Home/Shop, About, Contact.
3. Add something to the cart, then refresh the page — the cart should still be there (this proves localStorage works on the live
site).
4. Right-click the page and choose Inspect → Console. There should be no red errors. If you see red, something did not
upload or a path is wrong.
5. Click Inspect → Network, refresh, and check that style.css , app.js and products.json all show a status of 200 (success).
A status of 404 means that file is missing or the path is wrong.
On a phone:
1. Open WhatsApp or your email on the phone.
2. Send yourself the live URL (or type it carefully into the phone's browser).
3. Open the link. The site should load without any app.
4. Pinch and zoom; rotate the phone; check that the layout is still usable (this tests your responsive work from Session 9).
5. Test the cart and the contact form on the phone too.
Why the phone test matters: Most of your customers will open your site on a phone, not a laptop. A site that works only on a
big screen is not finished.
F.8 Writing a README.md
The idea. A README is the front page of your repository. The name means "read me." It is written in a simple formatting
language called Markdown, and the file is named README.md . GitHub displays it automatically below your file list.
Why every repository should have one. When a visitor, a classmate or an employer opens your repo, the README tells them
what the project is, what it does, and how to use it — without asking you. A project with no README looks unfinished.

Line-by-line notes:
# makes a big heading (the project name). ## makes a smaller sub-heading.
A line starting with - becomes a bullet point.
Backticks ` around a file or code name make it look like code.
A link in the form [text](url) becomes clickable. For the live-site line, learners may write the address plainly.
Worked example — editing the README on GitHub:
1. On the repository page, click the README.md file name.
2. Click the pencil icon (Edit this file) at the top right.
3. Replace the text with your own, using the template above.
4. Scroll down, and click Commit changes.

F.9 Summary of the session
Deploying means putting your site on an always-on server so anyone can open it.
Git = the tool that records versions, on your computer. GitHub = the website that hosts projects online.
Path A (web upload): create repo → Add file → Upload files → Commit changes → Settings → Pages → Deploy from a
branch → main → /(root) → Save.
Path B (Git): git init → git add . → git commit -m "..." → git remote add origin <url> → git push -u origin main .
The live URL is https://username.github.io/repo-name/ , and index.html must be at the top level.

## J. Real-World Case Study
<!-- kind:case_study -->
Situation. Mrs. Ngozi sells handbags from her shop and posts photos on Instagram. In her Instagram bio she has room for
exactly one link. She has been sending customers her WhatsApp number typed as text, but people keep mistyping it, and she
cannot show all her bags in a photo feed.
Relevant facts.
Instagram allows only one clickable link in the bio.
Mrs. Ngozi has 5 main bag designs and wants customers to see prices and a photo of each.
She does not have a developer and does not want to pay monthly fees.
She has heard that "websites cost money."
Decision point. How can one free link in her Instagram bio show all her products and let customers contact her?
Possible approaches.
1. Keep sending her WhatsApp number as text and hope customers type it correctly.
2. Pay a developer a large fee for a full e-commerce site.
3. Deploy a simple static product page to GitHub Pages for free, and put that URL in her Instagram bio.
Recommended solution (for this stage). Approach 3. A GitHub Pages site is free, gives her one clean link, shows all her
products with prices, and includes a contact form. A visitor taps the link, sees the bags, taps a bag, and fills the contact form —
which (in this course version) can be set to open the customer's email or WhatsApp with the message pre-filled.
Example of how it helps: The bio link becomes https://ngozi-bags.github.io/shop/ . Customers see photos, prices in naira, and a
"Contact me" button. No typo, no missed messages.
Trade-offs.
Approach 1 is free but loses sales to typos and looks unprofessional.
Approach 2 gives a full system (payments, stock, orders) but is expensive and overkill for five bags; and it still needs
maintenance.
Approach 3 is free, takes about an hour, and is live worldwide — but it is static: it cannot take automatic online payments.
For Mrs. Ngozi, contact-by-form or WhatsApp is enough for now, and she can upgrade later.
Professional connection. Being able to take an existing folder of files and turn it into a free public URL — with a README so
others understand it — is a core junior-developer skill. Many small businesses have exactly this need, and a freelancer who can
deploy to GitHub Pages can charge a fair fee for a task that costs the business nothing in hosting.

## K. Common Mistakes and Troubleshooting
<!-- kind:troubleshooting -->
Use this table as the live troubleshooting guide. Ask learners to check the relevant row before you give the answer.
K.1 The live site shows "404 — There isn't a GitHub Pages site here"
Symptoms: The URL opens but GitHub shows a 404 page. Likely/confirmed causes: (a) index.html is not at the top level of the
repository (it is inside a folder). (b) The file is named Index.html with a capital I. (c) GitHub Pages was never enabled, or was set
to the wrong branch/folder. How to investigate: Look at the repository file list — is index.html visible at the very top level?
Check Settings → Pages for the branch and folder. Confirm the exact spelling and case of the file name on GitHub. Corrective
steps: Move index.html to the top level; rename it to all lowercase; set branch main and folder / (root) ; click Save; wait 1–3
minutes. How to confirm resolved: The URL loads your site instead of the 404 page. Prevention: Always name the home page
index.html (lowercase) and keep it at the repository root.
K.2 "Your site is live" never appears
Symptoms: After saving Pages settings, no live message appears after several minutes. Likely causes: Pages not enabled; the
wrong branch selected; a build still in progress. Investigate: Refresh the Pages settings page; check the Actions tab for a
running or failed build. On the free plan, the first build can take a few minutes. Fix: Re-select Deploy from a branch, branch
main, folder / (root), and Save again. Wait, then refresh. Confirm: Green "Your site is live at ..." message appears. Prevent:
Upload the files before enabling Pages.
K.3 The page loads but has no styling (and no JavaScript behaviour)
Symptoms: Plain text, no colours; the cart button does nothing. Likely cause: css/style.css or js/app.js did not upload, or
the <link> / <script> path is wrong. Investigate: Press F12 → Network, refresh, and look for a red 404 next to style.css or
app.js . Also check the Console for red errors. Fix: Upload the missing files, or correct the path in the HTML to the correct
relative path. Confirm: Network shows 200 for both; styling returns. Prevent: Always upload the css and js folders, and use
relative paths.
K.4 Images do not load on the live site (but did on the laptop)
Symptoms: Broken-image icons; captions with no picture. Likely causes: (a) The images folder was not uploaded. (b) The file
name case differs ( Photo.JPG vs photo.jpg ) — Windows is not case-sensitive but GitHub Pages is. (c) The path is a Windows
absolute path like C:\... . Investigate: Network tab → find the image request → it shows 404. Compare the exact case of the
file name on GitHub with the path in your code. Fix: Upload the images; rename to match exactly (use all-lowercase file names);
change the path to a relative path such as images/bag-one.jpg . Confirm: Images appear. Prevention: Use lowercase names for
all files and folders; never use C:\ paths in web code.
K.5 The site shows an old version after I changed a file
Symptoms: You updated a file but the live site looks the same. Likely cause: The browser cached the old CSS/JS, or you did not
upload/push the change. Investigate: Hard-refresh with Ctrl + F5 . Check the repository to see whether the changed file is
actually there. Fix: If the file on GitHub is old, upload/push the change. If it is new, hard-refresh. Confirm: The new content
appears. Prevention: Hard refresh after every update; remember edits are not live until uploaded.
K.6 fetch of products.json fails on the live site
Symptoms: The product list is empty and the Console shows a red fetch error. Likely cause: The data folder (with
products.json ) was not uploaded, or the path is wrong. Investigate: In the Console, read the URL that failed. Open that URL
directly — you will get a 404 if the file is missing. Fix: Upload data/products.json ; correct the path in fetch(...) . Confirm:
Products appear. Prevention: Upload every folder your site uses.
Distinguish likely vs confirmed: A cause becomes confirmed only when you see the evidence — the 404 in the Network tab,
the wrong file name on GitHub, or the red Console error. Teach learners to confirm before changing code.
