# Capstone Build, Deploy and Present

## A. Session Identification
<!-- kind:identification -->
**Week / module:** Week 4 — Module 4: Polish and Deploy

**Recommended duration:** 105 minutes

**Difficulty:** Beginner, integrating all course skills

**Prerequisite knowledge:** Sessions 1–11. The learner must already have a multi-page site in progress, a product list from a JS array or products.json (Session 7), a cart with localStorage (Session 8), a validated contact form (Session 6), a responsive layout (Session 9), and a working GitHub Pages link (Session 11).

**Connection to previous work:** Every session built one piece of the capstone. This session assembles those pieces into the final Adaeze Fashion shop, checks each required feature against a rubric, deploys the finished site, and presents it (live demo + viva). It is the graduation session.

**Preparation before class:** Each learner's CEA-WebDev-Name folder (with capstone files) open; projectors for presentations; the rubric printed (one per learner and one per assessor); the instructor's own completed reference capstone deployed and ready to show; a score sheet for each presenter; the certificate-verification note ready (see the course-completion note at the end).

## B. Learning Outcomes
<!-- kind:outcomes -->
By the end of this session, the learner will be able to:
1. Assemble a complete 3–4 page interactive shop site (Home/Shop, About, Contact) that satisfies the capstone brief.
2. Verify their own work against a written checklist of required features before presenting.
3. Deploy the finished capstone to GitHub Pages and confirm a working public URL.
4. Demonstrate the live site, including add-to-cart, quantity change, removal and refresh persistence.
5. Explain one piece of their own code line by line in plain English, naming the file and the line.
6. Answer viva questions about variables, functions, the DOM, events, fetch , localStorage , validation, responsiveness and
deployment.
7. Reflect on what they have learned and state honestly what they can now do (a junior front-end beginner) and what they
should learn next.

## D. OPENING ACTIVITY (6 minutes)
<!-- kind:opening -->
Instructor setup: On the projector, open the instructor's own finished capstone live URL ( https://<instructor-
username>.github.io/<capstone-repo>/ ) on the Home/Shop page. Do not open any code.
What the instructor says:
"For twelve sessions you have learned one tool at a time — variables, functions, the DOM, events, fetch , localStorage ,
validation, responsive design, debugging, deployment. Each of those was a single brick. Today, look at this."
Then demonstrate quickly on the projector: type in the search box and watch products filter; click Add to cart two or three
times; change a quantity; show the running total in naira; then refresh the whole page and point at the cart still holding its
items. Say:
"Everything you see here is the work of the same skills you each have. This is not magic — it is the eleven sessions joined
together. Today is your day. Every one of you will show a live site like this, explain your own code, and answer a few
questions. Nobody leaves empty-handed, because the build work is almost done — today is about finishing, checking,
deploying and presenting."
Expected learner response: A mix of excitement and nervousness. Normalise the nerves:
"You are not being tested like an examination hall. You are presenting the thing you built. If something does not work, we
will fix it together, and that honesty is part of being a professional."
Why this opener works: It shows the finished destination, reframes the session as assembly rather than a new topic, and
reduces presentation fear by making the work already largely complete.

## E. PREREQUISITE REVIEW (7 minutes)
<!-- kind:prereq_review -->
Run this fast, as the capstone depends on every one of these. Put the questions on the projector and take quick answers.
Question 1: "What method loads products.json and turns the response into usable data?"
Expected answer: fetch('data/products.json').then(response => response.json()).then(data => renderProducts(data)) , with a
.catch(...) for errors.
Gap: learners forget .json() . Remind them: the first step gets the raw response; .json() converts it.
Question 2: "How do you open the browser's saved cart when the page loads?"
Expected answer: const cart = JSON.parse(localStorage.getItem('cart')) || []; — read the string and convert it back to an
array, with a fallback empty array if nothing is saved.
Gap: forgetting JSON.parse (cart comes back as a string) or forgetting the || [] fallback (first visit crashes).
Question 3: "A form should not reload the page when submitted. What stops it?"
Expected answer: call event.preventDefault() inside the submit handler.
Gap: learners read input values before the handler runs. Remind them the handler runs on submit.
Question 4: "Name the four function behaviours the cart must support."
Expected answer: add an item, change a quantity, remove an item, and show the running total.
Gap: forgetting quantity and remove. These are in the brief.
Question 5: "At which screen widths do we check responsiveness?"
Expected answer: a phone width (about 360px), a tablet width (about 768px), and a desktop width (about 1200px).
Bridge to today (say this):
"Those five answers are the heart of the capstone. Today we make sure each one is present, working, and deployed. Then
you present."
Gap handling: If the room is shaky on Questions 2 and 3, spend five minutes at the whiteboard writing
JSON.parse(localStorage.getItem('cart')) || [] and a short submit handler, because these two are the most common capstone
failure points.

## F. Full Lecture Notes
<!-- kind:lecture -->
F.1 What the capstone is
The idea. A capstone is the final project that proves you can combine everything you have learned into one working product. It
is not a new topic — it is the gathering-up of all twelve sessions.
Plain-English definition. The capstone is a 3–4 page interactive shop website for a small business. We use Adaeze Fashion, a
clothing shop in Port Harcourt, as the running example, but a learner may use their own chosen small business.
Why it exists. Employers and clients do not care how many lessons you watched. They care what you can build. The capstone
is the single artefact — a live URL — that you can show to a customer, a relative or a future employer to say: "I built this."
What "interactive" means here. The site is not a poster. It loads products from a file, filters them as you type, remembers a
cart that survives a refresh, checks a form before sending, and adapts to the screen size.
Real-life comparison. The capstone is like the final year project of a trade apprentice: not a test paper, but a finished piece of
furniture the carpenter can point to and say, "I made that." The customer can sit on the chair.
F.2 The pages of the capstone
The capstone has three to four pages, each served as an .html file:
1. Home / Shop ( index.html ) — the main page. It shows a heading and banner for Adaeze Fashion, a search box, a category
filter, and the product grid rendered from data/products.json . Each product card has a picture, a name, a price in naira, an
Add to cart button, and a quantity control.
2. About ( about.html ) — who Adaeze Fashion is: a short story, a photo, the business values. Static content is fine here; the
point is that the same navigation and footer appear on every page.
3. Contact ( contact.html ) — a validated contact form (name, email, message) with error messages and a success message
on valid submit.
4. (Optional fourth page) Cart ( cart.html ) — a dedicated page listing the cart items, quantities, subtotal and total. If you do
not make a separate page, show the cart in a panel on the shop page. Either is acceptable.
Consistency rule: every page must share the same header navigation and the same footer, and links must work between all
pages. A visitor must never get lost.
F.3 The required features (the capstone checklist)
Read this aloud and have learners tick Worksheet 12.1. These are non-negotiable for a passing capstone:
Product list rendered from a JavaScript array or from products.json using fetch .
Live search that filters products as the user types.
Category filter (at least two categories, e.g. Dresses, Bags, Shoes).
Add to cart with quantity for each product.
Cart persisted in localStorage so it survives a page refresh.
Running total displayed in naira (₦).
Validated contact form (required fields, email check, error messages, success message).
Responsive layout that works on phone, tablet and desktop.
A public deployed URL (GitHub Pages) that opens the finished site.
A README.md describing the project, features, how to run it, and the author.
Why these exactly. Each one maps to a session: the product list to Session 7 (fetch/JSON); search/filter to Session 7;
add/quantity/cart/total/persistence to Session 8; the validated form to Session 6; responsiveness to Session 9; deployment and
README to Session 11. The capstone is the course, made visible.
F.4 How the product list is built (recap of the core technique)
The shop page fetches the product data and renders cards. A minimal data/products.json :
```text
[
  { "id": 1, "name": "Ankara Dress", "price": 15000, "category": "Dresses", "image": "images/ankara-dress.jpg" },
  { "id": 2, "name": "Aso-Oke Set", "price": 42000, "category": "Dresses", "image": "images/aso-oke.jpg" },
  { "id": 3, "name": "Leather Handbag", "price": 18000, "category": "Bags", "image": "images/handbag.jpg" },
  { "id": 4, "name": "Beaded Sandals", "price": 9500, "category": "Shoes", "image": "images/sandals.jpg" }
]
```
The JavaScript that loads and renders it:
```text
let allProducts = [];
let currentCart = [];
```
```text
fetch('data/products.json')
  .then(response => response.json())
  .then(data => {
    allProducts = data;
    renderProducts(allProducts);
  })
  .catch(error => {
    console.error('Could not load products:', error);
  });
```
```text
function renderProducts(products) {
  const grid = document.getElementById('product-grid');
  grid.innerHTML = '';
  products.forEach(product => {
    const card = document.createElement('div');
    card.className = 'card';
    card.innerHTML = `
      <img src="${product.image}" alt="${product.name}">
      <h3>${product.name}</h3>
      <p class="price">₦${product.price.toLocaleString()}</p>
      <button onclick="addToCart(${product.id})">Add to cart</button>
    `;
    grid.appendChild(card);
  });
}
```
Line-by-line notes:
fetch('data/products.json') asks the server for the file. This only works from a server (Live Server or GitHub Pages), not from
a double-clicked file.
.then(response => response.json()) converts the response into a JavaScript array.
.then(data => { allProducts = data; renderProducts(data); }) keeps a copy in allProducts (so the filter can search it) and
draws the cards.
.catch(...) handles errors so the page does not fail silently.
toLocaleString() turns 15000 into 15,000 , so prices read nicely in naira.
F.5 Search and category filter (recap of Session 7)
```text
const searchBox = document.getElementById('search');
const categorySelect = document.getElementById('category');
```
```text
function applyFilters() {
  const text = searchBox.value.toLowerCase().trim();
  const category = categorySelect.value;
```
```text
  const filtered = allProducts.filter(product => {
    const matchesText = product.name.toLowerCase().includes(text);
    const matchesCategory = category === 'all' || product.category === category;
    return matchesText && matchesCategory;
  });
```
```text
  renderProducts(filtered);
}
```
```text
searchBox.addEventListener('input', applyFilters);
categorySelect.addEventListener('change', applyFilters);
```
Why .toLowerCase() on both sides: the search must ignore capitals. "dress" should find "Ankara Dress". This is one of the most
common capstone bugs — a filter that only works when the case matches exactly.
Why we keep allProducts : so that when the user clears the search, we filter from the full list, not from an already-filtered list.
Filtering the filtered list slowly loses items.
F.6 The cart: add, quantity, remove, total, and persistence (recap of Session 8)
The rule: always store data (id, quantity), never the HTML. Store the cart as an array of objects and re-render it after every
change.
```text
const CART_KEY = 'adaeze-cart';
```
```text
function loadCart() {
  const saved = localStorage.getItem(CART_KEY);
  currentCart = saved ? JSON.parse(saved) : [];
}
```
```text
function saveCart() {
  localStorage.setItem(CART_KEY, JSON.stringify(currentCart));
  renderCart();
}
```
```text
function addToCart(id) {
  const existing = currentCart.find(item => item.id === id);
  if (existing) {
    existing.qty += 1;
  } else {
    currentCart.push({ id: id, qty: 1 });
  }
  saveCart();
}
```
```text
function changeQty(id, delta) {
  const item = currentCart.find(item => item.id === id);
  if (!item) return;
  item.qty += delta;
  if (item.qty <= 0) {
    removeFromCart(id);
    return;
  }
  saveCart();
}
```
```text
function removeFromCart(id) {
  currentCart = currentCart.filter(item => item.id !== id);
  saveCart();
}
```
```text
function cartTotal() {
  let total = 0;
  currentCart.forEach(item => {
    const product = allProducts.find(p => p.id === item.id);
    if (product) total += product.price * item.qty;
  });
  return total;
}
```
Line-by-line notes:
localStorage.getItem(CART_KEY) reads a string. JSON.parse turns that string back into an array. If nothing is saved, we fall
back to [] .
JSON.stringify turns the array into a string before localStorage.setItem .
addToCart checks whether the item is already in the cart. If yes, it increases qty by 1; if no, it adds a new { id, qty } entry.
This is why clicking "Add to cart" twice should show quantity 2, not two separate rows.
changeQty uses delta (+1 or -1). If quantity drops to 0, the item is removed.
cartTotal looks up the price in allProducts and multiplies by the quantity, then adds everything up.
Every change calls saveCart() , which writes to localStorage and re-renders the cart badge and list.
Why prices are stored in naira as whole numbers: storing naira as integers avoids floating-point rounding errors (the
"₦0.30000000000000004" problem). If a shop ever uses kobo, store the smallest unit (kobo) as integers and divide only when
displaying.
F.7 The validated contact form (recap of Session 6)
```text
const form = document.getElementById('contact-form');
```
```text
form.addEventListener('submit', function (event) {
  event.preventDefault();
```
```text
  const name = document.getElementById('name').value.trim();
  const email = document.getElementById('email').value.trim();
  const message = document.getElementById('message').value.trim();
  const emailPattern = /.+@.+\..+/;
```
```text
  let errors = [];
  if (name === '') errors.push('Please enter your name.');
  if (!emailPattern.test(email)) errors.push('Please enter a valid email address.');
  if (message.length < 5) errors.push('Your message is too short.');
```
```text
  const feedback = document.getElementById('feedback');
  if (errors.length > 0) {
    feedback.style.color = 'red';
    feedback.textContent = errors.join(' ');
  } else {
    feedback.style.color = 'green';
    feedback.textContent = `Thank you, ${name}. Your message has been received.`;
    form.reset();
  }
});
```
Why preventDefault() first: without it, the browser reloads the page on submit and the JavaScript runs on a fresh, empty page.
Why .trim() : so a message of only spaces is treated as empty.
Why we collect all errors before showing them: the user sees every problem at once instead of fixing one, submitting, and
discovering another.
F.8 Responsive layout (recap of Session 9)
Responsiveness comes from three things:
1. The <meta name="viewport" content="width=device-width, initial-scale=1"> line in the <head> of every page.
2. A flexible layout (CSS flex or grid ) that wraps product cards.
3. Media queries that adjust for smaller screens.
```text
.product-grid {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(220px, 1fr));
  gap: 16px;
}
```
```text
@media (max-width: 600px) {
  .product-grid { grid-template-columns: 1fr; }
  nav ul { flex-direction: column; }
  body { font-size: 16px; }
}
```
How to verify: open the live site on a phone (about 360px wide), then on a tablet (about 768px) and a desktop (about 1200px).
The grid should show one column on the phone and more columns on wider screens, and the navigation should remain usable.
F.9 What "presenting" means
The idea. A presentation (also called a demo) is a short, spoken walkthrough of your finished work. In this course it lasts about
3 minutes per learner, followed by 2 minutes of viva (short questions).
Plain-English definition. A viva is an oral question-and-answer session where the instructor checks that you understand the
code you wrote — not just that it runs.
Why it matters professionally. Clients do not buy code; they buy confidence. A developer who can show a live site and explain
how it works wins the job. Being able to explain your own code line by line is the difference between "I copied a tutorial" and "I
can build for you."
What each learner does in the 3 minutes:
1. Open the live URL on the projector (not the local file).
2. Show the shop, type in the search box, use the category filter.
3. Add an item to the cart, change its quantity, show the running total in naira.
4. Refresh the page and show that the cart is still there (persistence).
5. Submit the contact form once with an error and once successfully.
6. Open one file in VS Code and explain one function line by line in plain English.
7. Answer the instructor's viva questions.
Honest expectation to set: the site does not have to be beautiful. It has to work and you have to understand it. A plain,
working, well-explained shop beats a fancy, broken one every time.
F.10 Summary of the session
The capstone is a 3–4 page interactive shop: Home/Shop, About, Contact (and optional Cart).
Required features: product list, live search, category filter, add-to-cart with quantity, localStorage persistence, naira total,

## J. Real-World Case Study
<!-- kind:case_study -->
Situation. Emmanuel finished this course three months ago. A small bakery, Sweet Crumb, asked him to build a website. He
built a 3-page site with a product list of cakes, a search box, a simple cart, a validated order form, and deployed it free on GitHub
Pages. He charged ₦45,000 for the build and showed the owner how to update prices by editing products.json .
Relevant facts.
The bakery had been taking orders only by phone and losing track of custom cake requests.
Emmanuel's site is static; it does not take online payment.
The owner can edit products.json and the order form opens the customer's email app with the order message pre-filled.
Within a month, the bakery reported more enquiries because customers could see prices and cake photos before calling.
Decision point. The owner now wants to (a) accept online payments and (b) let staff log in to mark orders as "ready".
Emmanuel must decide whether he can do this himself or must learn more first.
Possible approaches.
1. Tell the owner the site "cannot do that" and stop.
2. Try to fake payments and logins with JavaScript alone.
3. Explain honestly that payments and logins need a backend (a server with a database), and either learn backend next or bring
in a partner who knows it.
Recommended solution. Approach 3. This is the honest professional answer and the one that protects Emmanuel's reputation.
Static sites and GitHub Pages cannot securely take payments or verify a login, because anything in front-end JavaScript can be
seen and changed by the visitor. Emmanuel should say what the current site can do (show products, collect order messages,
filter, cart) and what needs a next step (a server).
Example — what Emmanuel says to the owner: "The current site is perfect for showing your cakes and collecting order
messages, and it costs nothing to host. To take payments safely and manage staff logins, we need a real server and database —
that is a different skill. I can learn it, or work with a partner. I will not fake it on the front end, because that would put your
customers' money at risk."
Trade-offs.
Approach 1 loses a client and is dishonest about what is possible.
Approach 2 is dangerous: a fake payment system can look real and lose the bakery money.

## K. Common Mistakes and Troubleshooting
<!-- kind:troubleshooting -->
Use this as the capstone's live troubleshooting guide.
K.1 The cart disappears after refreshing
Symptoms: Add to cart works, but after a page refresh the cart is empty. Likely/confirmed cause: The cart is not saved with
JSON.stringify , or not loaded with JSON.parse . Investigate: Open DevTools → Application → Local Storage and look at the
cart key. If it holds [object Object] or is missing, the save is wrong. If the Console shows a JSON.parse error, the load is wrong.
Fix: Save with localStorage.setItem(key, JSON.stringify(cart)) ; load with JSON.parse(localStorage.getItem(key)) || [] . Confirm:
The cart survives a refresh. Prevent: Always save after every cart change and load once at start-up.
K.2 The search or filter stops working (or "loses" items)
Symptoms: Typing a capital letter finds nothing, or after clearing the search some products are missing. Likely cause: Missing
.toLowerCase() on the typed text/product name, or filtering the already-filtered list instead of the full list. Investigate: Type the
product name in the exact same case as the data — if it works then, it is a case problem. Fix: Apply .toLowerCase() to both sides;
keep an untouched allProducts array and filter from it every time. Confirm: Any case finds the product; clearing search restores
all products. Prevent: Never overwrite allProducts when filtering.
K.3 Products do not appear on the live site (but appear locally)
Symptoms: The grid is empty online; the Console shows a red fetch error. Likely causes: products.json was not uploaded; the
path is wrong; or the page was opened without a server locally. Investigate: In the Console, read the failed URL; open it directly
(404 = missing file). Locally, confirm you are using Live Server, not a double-clicked file. Fix: Upload the data folder; correct the
path; always use a server for fetch . Confirm: Products appear locally and online. Prevent: Upload every folder; test on the live
URL.
K.4 "Cannot read properties of null (reading 'value')"
Symptoms: Red Console error; a feature does nothing. Likely cause: A typo between the HTML id and the
getElementById('...') in JavaScript, or the script runs before the element exists. Investigate: Copy the id from the HTML and
compare it letter-for-letter with the JS. Check that the <script> is at the bottom of the body. Fix: Match the ids exactly; keep
the script at the bottom. Confirm: The feature works and the error is gone. Prevent: Name ids carefully; test in the Console with
document.getElementById('theId') .
K.5 The contact form accepts empty inputs or reloads the page
Symptoms: Clicking submit reloads the page, or an empty form is "accepted". Likely cause: Missing event.preventDefault() , or
validation not checking .trim() . Investigate: Look at the submit handler — is preventDefault() the first line? Fix: Call
event.preventDefault() first; validate each field after trimming. Confirm: Empty submit shows a red error and does not reload.
Prevent: Always start a submit handler with preventDefault() .
K.6 The total is wrong or shows odd decimals
Symptoms: The total is off by small fractions (e.g. ₦300.00000000000006 ) or does not update. Likely cause: Floating-point maths
on prices, or the total is not recalculated after a change. Investigate: Log the individual line totals. Fix: Store naira as whole
numbers (or kobo as integers); recalculate the total inside saveCart() / renderCart() after every change. Confirm: The total is a
clean naira figure. Prevent: Avoid decimals in prices; re-render after every change.
K.7 The live URL shows an old version or a 404
Symptoms: The presentation link shows the previous version, or GitHub's 404 page. Likely cause: Changes were not
uploaded/pushed, the browser cached the old CSS/JS, or index.html is not at the repository root. Investigate: Open the
repository on GitHub and check the file is there; confirm index.html is at the top level. Fix: Upload/push; hard-refresh with Ctrl
+ F5 ; fix the file location. Confirm: The live URL shows the current site. Prevent: Re-deploy at the end of the sprint and test
before presenting.
Distinguish likely vs confirmed: check the Console, the Network tab or the Application tab and see the actual evidence before
changing code.

L.6 VIVA QUESTIONS WITH MODEL ANSWERS (instructor-only)
1. "What does localStorage store, and why do we convert with JSON.stringify and JSON.parse ?" → It stores strings only.
Our cart is an array of objects, so we stringify it to a string when saving and parse it back to an array when loading.
2. "Why does the search work whether I type 'dress' or 'Dress'?" → Because we call .toLowerCase() on both the typed text
and the product name before comparing.
3. "Show me where you add 1 to the cart quantity." → Points to the addToCart branch that does existing.qty += 1 , and
explains the find that checks whether the item already exists.
4. "Why do we need event.preventDefault() in the form?" → Without it, the browser reloads the page on submit and our
JavaScript runs on an empty page; preventDefault stops the default reload.
5. "Why must index.html be at the top level for GitHub Pages?" → The server looks for index.html as the default home
page in the root folder of the site; if it is inside a sub-folder, the root has no home page and returns a 404.
6. "What would happen if I opened your site by double-clicking the file instead of using a server?" → fetch would fail
due to browser security (CORS); that is why we use Live Server locally and GitHub Pages online.
7. "How did you make the site work on a phone?" → Viewport meta tag, a flexible grid/flex layout, and media queries tested
at phone width, tablet width and desktop width.
8. "If you had one more week, what would you add, and what would it require?" → E.g. online payments or customer
logins, which need a backend (server + database), because front-end code cannot keep secrets safely.
L.7 Common mistakes to avoid
Missing preventDefault ; forgetting JSON.stringify / parse ; forgetting .toLowerCase() in search; filtering the filtered list; wrong
id spelling causing null errors; not uploading folders so assets 404; and presenting from the local file instead of the live URL.

Common misconceptions to watch for and correct:
"The cart is stored on the server." → It is stored in each visitor's own browser ( localStorage ); it is per-device.
" localStorage can store the array directly." → It stores strings only; use JSON.stringify / parse .
"The site is only done if it looks beautiful." → Working and explainable beats pretty; design can improve later.
"Static sites can take payments." → They cannot securely; payments need a backend.
"Deploying is the end." → Deployment plus being able to explain the code is the real finish.
Suggested remedial exercises for learners who struggle:
1. Persistence drill: give a cart that saves but does not load, and ask the learner to fix JSON.parse .
2. Filter drill: give a search that is case-sensitive and ask them to fix it with .toLowerCase() .
3. Trace drill: give a fetch → render → filter chain and ask them to trace which function runs first.
4. Explain-aloud drill: have them teach one function to a partner before presenting to the class.
Differentiation:
Level 1 (supported): Provide a working reference capstone with products.json and the cart pre-filled; the learner works on
one or two features (e.g. render the grid, or fix validation) and presents those with support.

Level 3 (challenge): Add a product detail modal, a sort by price control, a separate cart.html page, or a "clear cart"
