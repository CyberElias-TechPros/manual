# Interactivity and Media

## A. Session Identification
<!-- kind:identification -->
**Week / module:** Week 4 — Module: Publishing and Capstone

**Recommended duration:** 105 minutes

**Difficulty:** Beginner (builds on Sessions 4–9)

**Prerequisite knowledge:** Sessions 1–9. Learners can build a styled, responsive multi-page site with a shared stylesheet, custom properties and media queries.

**Connection to previous work:** In Session 9 the Adaeze Fashion site became beautiful but static — nothing responds to the mouse, and there is no map or video. This session adds gentle CSS-only interactivity (hover, focus, transitions, simple animation and a show/hide trick) and richer media (responsive images, a Google Map, a YouTube video and a favicon). We deliberately stop short of JavaScript; real behaviour is a later course.

**Preparation before class:** Academy PCs on; VS Code and Chrome; each learner's styled site from Session 9 open; projector; a printed "Media & Interactivity Checklist"; Internet required for the map and video embeds; a sample square logo image for the favicon; the instructor's finished site ready to show.

## B. Learning Outcomes
<!-- kind:outcomes -->
By the end of this session, the learner will be able to:
1. Explain the difference between :hover , :focus and :active and when each applies.
2. Add smooth transition s so hover and focus changes animate instead of jumping.
3. Apply a simple transform (translate/scale/rotate) for a hover effect.
4. Create a basic @keyframes animation and attach it to an element.
5. Show and hide content using CSS only (the :hover reveal and the checkbox hack), and explain its limits.
6. Make images responsive with max-width: 100%; height: auto; and describe srcset , sizes and loading="lazy" at a basic
level.
7. Embed a Google Map on the contact page using an <iframe> copied from Google Maps.
8. Embed a YouTube video responsively using the aspect-ratio (or padding-bottom) technique.
9. Add a favicon so the browser tab shows the brand mark.
10. Apply three accessibility touches — keep visible focus outlines, write meaningful alt text, and ensure sufficient colour
contrast — and explain why each matters.

## D. OPENING ACTIVITY (6 minutes)
<!-- kind:opening -->
Instructor setup: On the projector, open the learner's finished Session 9 site. Slowly hover a nav link and a product card, click
into a form field, then — in a second tab — open the instructor's finished site where a button lifts, a card zooms, a "Delivery
info" panel slides open on hover, a map is embedded on the contact page and a video sits neatly on the shop page.
What the instructor says:
"Last week our site looked good — but it was like a shop with the lights off and the doors locked. Watch what happens
with small CSS touches: the link glows, the button lifts, the card breathes, a hidden panel reveals itself, and now there is a
map so customers can find Adaeze and a video so they can see the clothes move.
All of this today is still just HTML and CSS — no JavaScript. There is one rule I want you to carry out of this room: real, clever
interactivity — menus that open on click, forms that validate, buttons that calculate — needs a programming language
called JavaScript, and that is a whole later course. Today we learn what CSS alone can do, and how to add media like a
map and a video."
Expected learner response: Learners will enjoy the hover effects and ask "How did you make the panel open?" Accept the
excitement, and be honest: "Some of these tricks are simple; some have limits — I will show you both."
Why this opener works: It motivates the topic with visible, tactile effects while immediately setting an ethical boundary — the
learner knows exactly how far CSS goes and what JavaScript is for, which prevents both over-promising and confusion later.

## E. PREREQUISITE REVIEW (7 minutes)
<!-- kind:prereq_review -->
Run as a quick oral round-robin. Questions on the projector.
Question 1: "Why do all pages of a site use the same stylesheet?"
Expected answer: consistency and one-place updates.
Common gap: learners think it is only about saving typing. Emphasise consistency first.
Question 2: "What are CSS custom properties and how do we use them?"
Expected answer: named values stored on :root , used with var(--name) .
Common gap: writing var without () or forgetting the double hyphen. Show one live.
Question 3: "What CSS did we already use to change a nav link's colour when the mouse is over it?"
Expected answer: the :hover pseudo-class, e.g. nav a:hover { color: gold; } .
Common gap: some learners think that needed JavaScript. Confirm it is pure CSS.
Question 4: "What does display: grid do and where did we use it?"
Expected answer: lays children out in a grid; we used it for the product cards ( grid-template-columns: repeat(3, 1fr) ).
Common gap: confusing grid with flex. Grid = two dimensions (rows and columns); flex = mainly one direction.
Question 5: "What is a relative path and why does it matter?"
Expected answer: a path relative to the current file ( images/photo.jpg ); it makes files work on any machine, including the
web server.
Common gap: mixing \ (Windows) and / (web). On the web we always use forward slashes / .
Bridge to today (say this):
"Now that the site is consistent and responsive, we bring it to life. We will add small movements that guide the eye, reveal
hidden information, embed a map and a video, and — importantly — make sure we do not break accessibility while we do
it. Accessibility means a person using a keyboard or a screen reader can still use your site. That is not optional; it is
professional."
If more than a third of the class cannot answer Question 3, re-demonstrate a single :hover rule before continuing.

## F. Full Lecture Notes
<!-- kind:lecture -->
F.1 Pseudo-classes — reacting to the user's state
The idea. A pseudo-class is a keyword you add to a selector to style an element in a particular state — when the mouse is over
it, when it is focused, when it is being clicked, or when it is the first child, and so on.
Plain-English definition. A pseudo-class lets one element look different depending on what the user is doing with it, without
any extra class names or JavaScript.
Why it exists. Users need feedback. If a button looks identical whether or not you are hovering it, and whether or not it is
focused, people do not know what is clickable or where they are. Feedback is usability.
Analogy. Think of a nylon shirt under a light. It is the same shirt, but it looks different depending on the light. The shirt did not
change; its appearance reacted to a condition. Pseudo-classes are the "light".
The three we use today:
Pseudo-class Applies when… Example
```text
:hover
```
the mouse pointer is over the element
```text
a:hover { color: gold; }
```
```text
:focus
```
the element is selected (clicked into, or reached with the Tab key)
```text
input:focus { border-color: gold; }
```
```text
:active
```
the element is being pressed down right now
```text
.button:active { transform: scale(0.98); }
```
Syntax note. You write them attached to a selector with a colon: selector:hover { ... } . The gap between selector and
:hover matters — a :hover (with a space) means something completely different (a hovered descendant of a ). No space: the
element itself.
Worked example:
```text
nav a:hover { color: var(--color-gold); }
.contact-form input:focus { border-color: var(--color-gold); }
.button:active { transform: scale(0.98); }
```
Expected browser result: hover a nav link → it turns gold; click into an input → its border turns gold; press and hold a button →
it shrinks slightly under your finger.
Misconception. :hover does not exist on touchscreens in the same way; on a phone there is no mouse. This is one reason we
also style :focus and never rely on hover for essential information. Always make sure important content is visible without
hover.
Limitation. Pseudo-classes only respond to state. They cannot store information, do calculations, or respond to a click that
toggles something permanently — that needs JavaScript (or the checkbox trick in F.5).
F.2 Transitions — making changes smooth
The idea. A transition tells the browser: "when this property changes, do not jump — animate it over a short time."
Why it exists. An instant colour snap feels cheap and jarring. A 0.3-second fade feels polished and helps the eye follow the
change.
Analogy. A dimmer switch versus a normal light switch. Both end at "light on", but the dimmer glides and feels expensive. A
transition is the dimmer switch for CSS values.
Syntax:
```text
selector {
  transition: property duration timing-function;
}
```
property — what to animate ( color , background-color , transform , or all ).
duration — how long, e.g. 0.3s or 300ms .
timing-function — the feel; ease (gentle start and end) is the common default, ease-in-out is even softer, linear is
mechanical.
Worked example:
```text
.button {
  background-color: var(--color-gold);
  transition: background-color 0.3s ease, transform 0.2s ease;
}
.button:hover {
  background-color: var(--color-gold-dark);
  transform: translateY(-2px);
}
```
Line by line:
The transition lists two properties separated by a comma: background colour over 0.3s and transform over 0.2s.
translateY(-2px) moves the element 2px up (negative y is up) on hover.
Because the transition is on the base .button (not on :hover ), the animation plays both on entering and leaving the hover
state.
Expected browser result: the button darkens and lifts gently over a third of a second; release the mouse and it glides back
down.
Misconception. Learners put transition inside the :hover rule. Then the animation runs into hover but snaps back instantly.
The transition belongs on the base selector.
Performance note. color , background-color and transform are cheap to animate. Animating width , height or left/top
forces the browser to recalculate layout and can stutter. Prefer transform and opacity where possible.
F.3 Transforms — moving, scaling and rotating
The idea. transform changes how an element is drawn — moved, scaled, rotated or skewed — without affecting the position
of other elements.
Why it exists. It lets you create motion (lift, zoom, turn) cheaply and without breaking the layout around it. That last point is the
key advantage: unlike changing margin or width , a transform does not push neighbours around.
The functions we use:
Function Effect Example
```text
translateY(-2px)
```
move up 2px button lift
```text
scale(1.05)
```
grow 5% image zoom on hover
```text
rotate(90deg)
```
turn 90° an arrow that rotates
Worked example — an image that zooms on hover:
```text
.product img {
  transition: transform 0.4s ease;
}
.product:hover img {
  transform: scale(1.06);
}
```
Note the selector .product:hover img — "when the card is hovered, transform its image". This is a descendant selector
combined with a pseudo-class, a very common professional pattern. Hover anywhere on the card and the photo zooms.
Expected browser result: moving the mouse over a product card gently enlarges its photo by 6%; moving away shrinks it back.
Important overflow note. If the zoomed image spills outside the card, add overflow: hidden; to the card so the overflow is
clipped neatly:
```text
.product { overflow: hidden; }
```
Misconception. Learners think transform deletes the element or changes the document flow. It does neither — it is purely
visual.
F.4 Keyframe animations — motion without a trigger
The idea. A transition needs a change (like hover) to fire. An animation with @keyframes can play by itself, in a loop or once, the
moment the page loads.
Why it exists. Sometimes you want motion that is not caused by the user: a gentle fade-in as the hero appears, a soft pulsing
badge on a "Sale" tag.
Analogy. A transition is a door that swings when pushed. An animation is a wind-up toy that keeps moving on its own once you
set it going.
Syntax:
```text
@keyframes fadeIn {
  from { opacity: 0; }
  to   { opacity: 1; }
}
```
```text
.hero {
  animation: fadeIn 1s ease-in;
}
```
@keyframes fadeIn defines the motion and gives it a name.
from { opacity: 0; } is the start (invisible), to { opacity: 1; } is the end (fully visible).
animation: fadeIn 1s ease-in; attaches it: name, duration, feel.
opacity: 0 means fully transparent; 1 means fully solid.
A slightly richer example — a gentle float loop:
```text
@keyframes float {
  0%   { transform: translateY(0); }
  50%  { transform: translateY(-6px); }
  100% { transform: translateY(0); }
}
.badge {
  animation: float 3s ease-in-out infinite;
}
```
Using 0% / 50% / 100% gives three stages. infinite makes it loop forever.
Expected browser result: the hero fades in once on load; the badge bobs gently up and down forever.
Misconception / important caution. Do not over-animate. Constant motion is distracting and can be uncomfortable for some
users. Use animation sparingly (one or two per page). Also, some users set an operating-system preference for reduced motion;
we can respect it:
```text
@media (prefers-reduced-motion: reduce) {
  * { animation: none; transition: none; }
}
```
This small block is a mark of a thoughtful designer.
F.5 Showing and hiding content with CSS only
The idea. CSS can reveal or hide a panel without JavaScript. Two beginner-safe ways: a :hover reveal and the "checkbox hack".
Way 1 — hover reveal. The simplest. A hidden panel appears while you hover its parent.
```text
.delivery-info {
  max-height: 0;
  overflow: hidden;
  transition: max-height 0.4s ease;
}
.hero:hover .delivery-info {
  max-height: 200px;
}
```
We animate max-height from 0 to a generous 200px and clip with overflow: hidden .
Limitation: this only works with a mouse. On a phone or with a keyboard there is no hover, so a touch user may never see
the panel.
Way 2 — the checkbox hack. A hidden checkbox stores an on/off state; CSS reacts to :checked . This works on click (including
on touch) and with the keyboard.
The HTML:
```text
<input type="checkbox" id="menu-toggle" class="visually-hidden">
<label for="menu-toggle" class="menu-btn">Menu</label>
<nav class="mobile-nav">
  <ul>
    <li><a href="index.html">Home</a></li>
    <li><a href="shop.html">Shop</a></li>
    <li><a href="about.html">About</a></li>
    <li><a href="contact.html">Contact</a></li>
  </ul>
</nav>
```
The CSS:
```text
.visually-hidden {
  position: absolute;
  width: 1px; height: 1px;
  overflow: hidden;
  clip: rect(0 0 0 0);
}
```
```text
.menu-btn {
  display: none;   /* hidden on desktop */
  cursor: pointer;
  color: var(--color-cream);
}
```
```text
.mobile-nav {
  display: none;
}
```
```text
#menu-toggle:checked ~ .mobile-nav {
  display: block;
}
```
Line by line:
The checkbox is visually hidden but still focusable (better for accessibility than display: none ).
The <label> is clickable because its for="menu-toggle" matches the checkbox's id ; clicking the label toggles the checkbox.
#menu-toggle:checked ~ .mobile-nav uses the general sibling combinator ~ ("a following sibling") and the :checked
pseudo-class: "when the checkbox is checked, show the nav that follows it."
On a real mobile menu you would only show .menu-btn inside a mobile media query.
Expected browser result: clicking the word "Menu" shows the list; clicking again hides it.
Honest limitation (say this clearly): the checkbox hack is a clever trick with real drawbacks — it cannot easily close the menu
when you tap a link, it becomes messy with multiple menus, and it does not give screen readers helpful "expanded/collapsed"
information. Real, reliable interactivity — open/close menus, tabs, sliders, live search, form validation — is done with
JavaScript. That is taught in the Web Development course. Treat the checkbox hack as an introduction to the idea of state, not
as the professional solution.
Misconception. Learners think CSS can "remember" a click. It cannot. The checkbox hacks works only because a form control
(the checkbox) is holding the state for us. Without a control to hold state, CSS cannot.
F.6 Responsive images
The idea. An image should never be wider than its container, and on small screens it should shrink instead of overflowing.
Why it exists. Large photos are one of the top causes of slow, broken-looking mobile pages. Making images fluid is step one.
The core rule:
```text
img {
  max-width: 100%;
  height: auto;
}
```
max-width: 100% stops an image growing past its container.
height: auto keeps the image's natural proportions so it does not squash.
The width / height attributes — preventing layout jump. In the HTML, add the image's real dimensions:
```text
<img src="images/hero.jpg" alt="Adaeze Fashion studio in Port Harcourt" width="1200" height="600">
```
The browser reserves a 2:1 space before the image loads, so the page does not jump when it appears (a nice performance and
usability win). The CSS rule above still keeps it fluid.
Lazy loading. Images far down the page need not load until the user scrolls to them:
```text
<img src="images/product-1.jpg" alt="Ankara gown" loading="lazy" width="600" height="800">
```
loading="lazy" tells the browser to defer off-screen images, speeding up the first view.
A brief word on srcset and sizes (awareness only). For serious performance, you can offer several sizes of the same image
and let the browser choose:
```text
<img
  src="images/product-1-600.jpg"
  srcset="images/product-1-400.jpg 400w, images/product-1-800.jpg 800w"
  sizes="(max-width: 767px) 100vw, 300px"
  alt="Ankara gown" loading="lazy">
```
This means: "here are 400px and 800px versions; on phones use full width, otherwise a 300px slot." You do not need to master
this today — just know it exists, because it is how large commercial sites stay fast.
Expected browser result: resize the window and images shrink with their column, never causing a horizontal scrollbar.
Misconception. Learners think setting width: 100% on all images is always best. It is not — sometimes you want a small logo to
stay small. max-width: 100% is safer because it caps size without forcing full width.
F.7 Embedding a Google Map (contact page)
The idea. Google lets you copy a ready-made <iframe> that shows a map of any place, including a pin and address. You paste it
into your page.
Why it exists. Customers need to find the business. A map removes the "where exactly are you?" phone call, which is huge for a
small Port Harcourt shop.
What an iframe is. An iframe (inline frame) is a small window inside your page that shows another web page — here,
Google's map. It is the same idea for the video in F.8.
The steps (in the browser):
1. Go to google.com/maps.
2. Search for the place, e.g. "24 Ebony Road, Port Harcourt". A marker appears.
3. Click Share (or the three-dot menu) → Embed a map.
4. Choose a size, then click Copy HTML.
5. Paste the copied <iframe> into your contact.html where the map should appear.
The embed code (the src will be a long Google link in real use; shown shortened here):
```text
<iframe
  src="https://www.google.com/maps/embed?pb=..."
  width="600" height="450"
  style="border:0;"
  allowfullscreen=""
  loading="lazy"
  referrerpolicy="no-referrer-when-downgrade"
  title="Map showing Adaeze Fashion, Port Harcourt">
</iframe>
```
Line by line:
src — the special Google link that loads the map. This is why internet is required.
width / height — the default size; we override this with CSS below.
style="border:0" — removes the default frame border.
allowfullscreen — lets the map expand to full screen.
loading="lazy" — the map loads only when scrolled near (better speed).
title — describes the iframe for screen-reader users; always add this.
Making the map responsive (fill the width):
```text
.map-container {
  max-width: 800px;
  margin: 0 auto;
}
.map-container iframe {
  width: 100%;
  height: 380px;
  border: 0;
  border-radius: 10px;
}
```
Expected browser result: a rounded map showing a pin on 24 Ebony Road, sized to the page and shrinking with it on mobile.
Accuracy note. You cannot build a map by hand — the embed is Google's own page shown through an iframe. If the internet is
down, the area shows blank or a "cannot load" message. That is expected, not a bug in your code.
Limitation. The embed shows a map. Google's free embed does not give you live turn-by-turn directions or unlimited styling.
For a basic "find us" map, it is perfect.
F.8 Embedding a YouTube video responsively (aspect-ratio)
The idea. Copy YouTube's embed <iframe> for the video, then wrap it so it keeps its 16:9 shape and shrinks on small screens.
Why it exists. Video is the best way for a fashion brand to show fabric moving and colours in real light. A responsive video
keeps the layout tidy on a phone without squashing or letterboxing badly.
The steps (in the browser):
1. Open the video on youtube.com.
2. Click Share → Embed.
3. Click Copy.
4. Paste the <iframe> into shop.html , wrapped in a container.
The modern technique — aspect-ratio :
```text
<div class="video-container">
  <iframe
    src="https://www.youtube.com/embed/VIDEO_ID"
    title="Adaeze Fashion — Ankara collection preview"
    allow="accelerometer; clipboard-write; encrypted-media; gyroscope; picture-in-picture"
    allowfullscreen>
  </iframe>
</div>
```
```text
.video-container {
  max-width: 760px;
  margin: 0 auto;
}
.video-container iframe {
  width: 100%;
  aspect-ratio: 16 / 9;
  border: 0;
  border-radius: 10px;
}
```
aspect-ratio: 16 / 9 tells the box to keep a widescreen shape; when the width changes, the height follows automatically.
This is the clean, modern way.
VIDEO_ID is the short code after watch?v= (or after youtu.be/ ) in the video's URL. Note embed and watch?v= are different
links — the embed one is what an iframe needs.
The older technique (still common) — the padding-bottom trick: if a browser does not support aspect-ratio , use this:
```text
.video-container {
  position: relative;
  width: 100%;
  height: 0;
  padding-bottom: 56.25%; /* 9 ÷ 16 = 0.5625 → 16:9 */
  overflow: hidden;
}
.video-container iframe {
  position: absolute;
  top: 0; left: 0;
  width: 100%; height: 100%;
  border: 0;
}
```
padding-bottom: 56.25% builds a box whose height is 56.25% of its width — exactly 16:9. The iframe is then stretched to fill
that box absolutely.
Know both; modern sites increasingly use aspect-ratio .
Expected browser result: a rounded video that fills the column on desktop and shrinks neatly on mobile, always keeping a
movie-like shape.
Accuracy note. The video streams from YouTube's servers, so internet is required. If a video is private, embeddable is disabled
by its owner, or the VIDEO_ID is wrong, you will see "Video unavailable". Check the video is public and embeds are allowed.
Limitation. You are embedding someone's video on their terms (YouTube branding, suggestions, ads may appear). For a fully
controlled player you would host the video yourself — a topic for later.
F.9 Favicon basics
The idea. A favicon ("favourite icon") is the tiny square icon shown on the browser tab and in bookmarks. It is your brand's
smallest, most-seen logo.
Why it exists. A tab with a real icon looks professional and is easy to find among ten open tabs; a blank page icon looks
unfinished.
The file. A small square image, ideal size 512×512 (browsers scale it down). PNG or ICO both work; .ico is the traditional
format. For best results, keep it simple — a logo mark, not tiny text.
Linking it (in the <head> of every page):
```text
<link rel="icon" type="image/png" href="images/favicon.png">
```
Line by line:
rel="icon" — tells the browser this is the tab icon.
type="image/png" — the file type.
href="images/favicon.png" — the relative path to the icon.
Expected browser result: after a refresh, the Adaeze Fashion "A" mark appears on the browser tab.
Misconception. Learners expect the icon to update instantly. Browsers cache favicons aggressively; if it does not change, close
the tab and reopen, or hard-refresh with Ctrl+F5 . This is normal, not a code error.
Limitation. The favicon does not change the page itself, only the tab. And a busy, detailed logo will look like a blur at 16×16
pixels — keep it simple.
F.10 Accessibility — the professional non-negotiable
The idea. Accessibility (often shortened to "a11y") means building so that everyone can use your site — including people using
a keyboard instead of a mouse, people with low vision, and people using a screen reader.
Why it exists. Roughly, disabled people are a large part of every market, and accessible sites are also easier for everyone. More
importantly, it is the right thing to do: a business website that only works for sighted mouse users excludes real customers.
Three touches we apply today:
1. Keep a visible focus outline. When a keyboard user presses Tab , the focused element must be clearly visible. Never do this
alone:
```text
/* BAD — removes the only sign of keyboard focus */
a:focus { outline: none; }
```
If you dislike the default ring, replace it with something at least as clear:
```text
a:focus-visible {
  outline: 3px solid var(--color-gold);
  outline-offset: 2px;
}
```
:focus-visible shows the ring for keyboard users but not when a mouse user clicks — the best of both worlds.
2. Write meaningful alt text. alt is the text that describes an image for screen-reader users (and shows if the image fails to
load).
```text
<!-- BAD: no description -->
<img src="images/product-1.jpg" alt="">
```
```text
<!-- BAD: "image" tells the user nothing -->
<img src="images/product-1.jpg" alt="image">
```
```text
<!-- GOOD: describes the content -->
<img src="images/product-1.jpg" alt="Ankara gown in gold and brown, full length">
```
```text
<!-- GOOD: decorative image, intentionally empty -->
<img src="images/divider-line.png" alt="">
```
Rule of thumb: describe the content and function of the image. If an image is purely decorative, an empty alt="" is correct (it
tells the screen reader to skip it).
3. Ensure sufficient colour contrast. Text must stand out from its background. The widely used guideline is a contrast ratio of
at least 4.5:1 for normal body text and 3:1 for large text. Light grey text on white, or gold text on cream, often fails.
Good: charcoal #333 on cream #f5f0eb .
Risky: light gold #d4a574 on cream — use dark brown text instead for body copy.
The Chrome DevTools colour picker shows the contrast ratio and a tick or cross; we explore this properly in Session 11.
Expected result after applying all three: you can Tab through the whole page and always see where you are; a screen reader
announces each image sensibly; body text is easy to read.
Misconception. "Accessibility is extra work for a few people." In practice it is small habits that make the site better for everyone
— clearer focus, better descriptions, readable text. It is part of doing the job well, not an add-on.
F.11 Summary of the session
:hover , :focus and :active give feedback on user state — pure CSS.
transition makes changes smooth; put it on the base rule, not on :hover .
transform moves/scales/rotates without disturbing layout; pair with overflow: hidden for zooms.
@keyframes + animation create motion that can run by itself — use sparingly.
Show/hide with CSS only: the :hover reveal (mouse-only) or the checkbox hack (works on click) — but real interactivity
needs JavaScript, a later course.
Responsive images: max-width: 100%; height: auto; , plus width / height , loading="lazy" and (awareness) srcset .
Embed a Google Map and a YouTube video by pasting their <iframe> s; make the video responsive with aspect-ratio .
Add a favicon to every page.
Accessibility: keep a visible focus outline, write meaningful alt text, ensure contrast ≥ 4.5:1.

## K. Common Mistakes and Troubleshooting
<!-- kind:troubleshooting -->
K.1 Hover effect animates in but snaps back out
Symptoms: The colour/movement glides on hover but jumps instantly on mouse-out. Likely cause: The transition was
written inside the :hover rule. Corrective steps: Move the transition to the base selector. Prevention: Always put the
transition on the element's normal rule. Confirm resolved: Both entering and leaving are smooth.
K.2 Video looks stretched or squashed
Symptoms: The video is distorted or the black bars are wrong. Likely cause: A fixed height fighting the width, or no aspect
ratio set. Corrective steps: Remove fixed heights; set width: 100%; aspect-ratio: 16 / 9; on the iframe inside a wrapper.
Prevention: Let the wrapper control width and aspect-ratio control shape. Confirm resolved: The video keeps a movie shape
at every window size.
K.3 Map or video area is blank
Symptoms: An empty grey box where the map/video should be. Likely causes: (a) No internet. (b) Wrong src / wrong
VIDEO_ID . (c) The video is private or embeds are disabled. How to investigate: Open the iframe src in a new browser tab. If it
loads there, the embed code is fine and the issue is elsewhere; if it errors, the link is wrong or the media is restricted. Corrective
steps: Re-copy the embed code; ensure the video is public; restore internet. Prevention: Test embeds immediately after
pasting. Confirm resolved: The map shows a pin / the video shows a play button.
K.4 Favicon will not change
Symptoms: The old or no tab icon appears. Likely cause: The browser cached the favicon. Corrective steps: Hard-refresh
( Ctrl+F5 ) or close and reopen the tab; confirm the href path and file exist. Prevention: Keep favicon.png inside images/ and
reference it correctly. Confirm resolved: The brand mark appears on the tab.
K.5 The zoomed image spills outside the card
Symptoms: On hover, the enlarged image overflows its rounded card. Likely cause: The card has no overflow: hidden; .
Corrective steps: Add overflow: hidden; to the card. Confirm resolved: The zoom stays inside the rounded card.
K.6 No focus outline when tabbing
Symptoms: Pressing Tab shows no visible highlight. Likely cause: A rule like a:focus { outline: none; } (perhaps copied from
the internet) removed it. Corrective steps: Remove it, or replace with a:focus-visible { outline: 3px solid var(--color-gold);
outline-offset: 2px; } . Prevention: Never remove a focus outline without providing a visible replacement. Confirm resolved:
You can see where focus is at every Tab press.
K.7 Screen reader cannot tell what an image is
Symptoms: A screen reader reads "image" or reads nothing useful. Likely cause: Missing or meaningless alt text. Corrective
steps: Write a short description of the image's content/function; use alt="" only for purely decorative images. Confirm
resolved: The description makes sense when read aloud on its own.
Distinguish likely vs confirmed: Confirm before fixing — open the embed's src in a tab, check the overflow value in
DevTools, look for the removed outline rule. Guessing wastes time.

## N. Reflection and Recap
<!-- kind:reflection -->
Plain-English summary. Today you gave the site a sense of touch. You used :hover , :focus and :active to give feedback,
transition to make changes glide, transform to lift and zoom without disturbing the layout, and @keyframes for motion that
runs by itself. You learned two CSS-only ways to show and hide content — and, importantly, their limits: real interactivity needs
JavaScript, which is a later course. You made images responsive and lazy, embedded a real Google Map and a responsive
YouTube video, added a favicon, and applied three accessibility essentials: a visible focus outline, meaningful alt text and
sufficient contrast.
Five important takeaways:
1. :hover / :focus / :active give state-based feedback — pure CSS.
2. Put transition on the base rule, and prefer transform / opacity for smoothness.
3. Real interactivity (menus, validation, sliders) needs JavaScript; CSS tricks have limits.
4. Embeds are other people's pages shown in an <iframe> ; make the video responsive with aspect-ratio .
5. Never break accessibility: keep focus visible, describe images, keep contrast ≥ 4.5:1.
Questions to help you recognise what you can now do:
Can I make a button lift smoothly on hover without JavaScript?
Can I explain why the checkbox hack is not a real menu?
Can I embed a map and a video that both behave on a phone?

## O. Instructor Evaluation Notes
<!-- kind:instructor_notes -->
Observable signs of genuine competence:
Learner writes the transition on the base rule and can explain why.
Learner uses transform for the zoom and adds overflow: hidden without being told.
Learner can state, unprompted, that real interactivity requires JavaScript.
Learner embeds the video with aspect-ratio and the map accurately, and tests both.
Learner adds meaningful alt text rather than "image", and does not delete the focus outline.
Learner tests with the keyboard (Tab) as well as the mouse.
Common misconceptions to watch for and correct:
"CSS can make a proper menu / remember clicks." → Only via a control like a checkbox; real behaviour needs JavaScript.
"Removing the outline makes it look cleaner." → It makes the site unusable for keyboard users; replace, never remove.
" alt is optional / can be 'image'." → It carries the content for screen readers.
"Hover works on phones." → There is no hover on touch; never hide essential content behind hover alone.
"Transitions belong on :hover ." → They belong on the base rule.
Suggested remedial exercises for learners who struggle:
1. Snap vs glide: give one button with the transition misplaced and one correct; ask the learner to identify which is smooth on
exit.
2. Alt-text rewrite: provide five images with poor alt values and ask for meaningful replacements (and one decorative
alt="" ).
3. Embed fix-up: hand a page whose video is stretched and whose map is blank; ask the learner to fix the aspect ratio and
check the src .
Differentiation:
Level 1 (supported): Provide the CSS blocks pre-written to paste, and guide the learner through the two embeds only.
Level 2 (standard): The exercise and assignment as written.
Level 3 (challenge): Add a CSS-only "back to top" using scroll-behavior: smooth and an anchor link; add a second
@keyframes (slide-in) with a delay; test contrast ratios in DevTools and adjust the palette to pass 4.5:1.
Timing guidance: Embeds need internet and can be slow; if connectivity is poor, do the video first (smaller payload) and
demonstrate the map only on the projector. Protect the transitions and accessibility steps — those carry the real learning.
