# Final Project: Capstone — Finalise, Publish and Present

## A. Session Identification
<!-- kind:identification -->
**Week / module:** Week 4 — Module: Publishing and Capstone

**Recommended duration:** 105 minutes

**Difficulty:** Beginner, integrating all skills from Sessions 1–11

**Prerequisite knowledge:** Sessions 1–11. Learners can plan a site, build semantic multi-page HTML, style it with an organised external stylesheet, make it responsive, add CSS interactivity and media, and test and debug it.

**Connection to previous work:** Everything in the course leads here. The website the learner has been building since Session 7 (planning) and Session 8 (structure) and styling since Session 9 becomes a complete 3–5 page responsive business website. This session is where the learner finalises it, verifies it against a professional rubric, optionally publishes it, and presents it with a viva.

**Preparation before class:** Academy PCs on; VS Code and Chrome; every learner's project accessible; projector for presentations; printed capstone briefs (one per learner), printed rubrics (one per learner), and certificate sign-off sheets; internet for optional publishing (GitHub/Netlify); a timer visible to the class; the instructor's own finished Adaeze Fashion site ready as the benchmark.

## B. Learning Outcomes
<!-- kind:outcomes -->
By the end of this session, the learner will be able to:
1. Finalise a complete 3–5 page responsive business website that meets the capstone brief.
2. Audit their own site against a professional rubric and identify any last gaps.
3. Apply final polish to structure, design, responsiveness, content, the form, code quality and accessibility.
4. Validate and test the finished site on desktop and mobile, and explain the results.
5. Optionally publish the website to a free host and obtain a public URL.
6. Present the website to the class confidently, demonstrating its features.
7. Answer viva questions about their design and technical decisions in plain English.
8. Reflect honestly on their learning and describe realistic next steps.

## D. OPENING ACTIVITY (5 minutes)
<!-- kind:opening -->
Instructor setup: On the projector, show three images/tabs: (1) a blank page, (2) the learner's own Session 8 skeleton if it still
exists, and (3) the instructor's finished Adaeze Fashion site.
What the instructor says:
"Four weeks ago, most of you had never written a line of code. Today you will present a real, working business website that
you built yourselves — a site for Adaeze Fashion that a real customer could use. Look at where we started and where we
are.
There will be no new lessons today. Today is about finishing well and presenting well. I am going to give you a brief and a
rubric — the same kind of checklist a real client uses — and you are going to bring your site up to that standard, publish it
if you can, and show it to us. A beautiful website you cannot explain is not enough; a site you understand and can defend
is the goal. Let us finish strong — From Zero to Expert, Together."
Expected learner response: A mix of nervousness and pride. Reassure them: the rubric is not a trick; it lists exactly what we
practised, and the viva is a conversation, not an interrogation.
Why this opener works: It frames the session as celebration and consolidation rather than new content, reduces performance
anxiety with transparency, and reminds learners of the journey — which builds the confidence needed to present.

## E. PREREQUISITE REVIEW (7 minutes)
<!-- kind:prereq_review -->
Run fast. This doubles as the final revision before the viva, so let several learners answer each.
Question 1: "What are the three building blocks of a website, and what does each do?"
Expected: HTML (structure/content), CSS (appearance), JavaScript (behaviour — not used in this course's sites).
Gap handling: remind them our capstone is HTML + CSS only, and JavaScript is the next course.
Question 2: "What are the four layers of the box model?"
Expected: content, padding, border, margin.
Gap: padding (inside) vs margin (outside).
Question 3: "What does display: flex do and where did we use it? What about display: grid ?"
Expected: flex for the header/nav (one direction); grid for the product cards (rows and columns).
Gap: flex goes on the parent container.
Question 4: "What is a media query, and which breakpoints did we use?"
Expected: CSS that applies under a condition, usually screen width; 1023px (tablet) and 767px (mobile).
Gap: forgetting the parentheses.
Question 5: "Why do all pages share one stylesheet?"
Expected: consistency and one-place updates.
Gap: the value is consistency first.
Question 6: "How do you test a site before publishing?"
Expected: click links, check images, use the device toolbar, check the Console, validate HTML/CSS, check
contrast/alt/labels, try a second browser.
Gap: testing only on the Home page.
Question 7: "What is a relative path, and why does it matter when publishing?"
Expected: a path relative to the current file, with forward slashes; absolute paths break on a web server.
Gap: backslashes vs forward slashes.
Question 8: "In one sentence, what did you learn that surprised you most?"
Accept any sincere answer. This warms the room and seeds the reflection.
Bridge to today: "Every answer you just gave is something on the rubric. If you can explain them — as you just did — you can
pass the viva. Now finish your site and show it."
If the room is weak on the media-query or path questions, spend five extra minutes on those two, since they cause the most
capstone failures.

## F. Full Lecture Notes
<!-- kind:lecture -->
F.1 What the capstone is and why it matters
The idea. The capstone is the final project that proves you can do the whole job end to end: plan, build, style, make responsive,
add media, test, and present a complete business website.
Plain-English definition. A capstone is a single, substantial piece of work that draws together every skill from the course, the
way a final year project draws together a degree.
Why it exists. Knowing individual skills (a media query, a flexbox header) is not the same as producing a finished website under
your own judgement. The capstone tests the whole, including decisions, testing and explanation. This is what employers and
clients actually pay for.
Analogy. Learning to sew a hem, a collar and a sleeve is not the same as producing a finished gown that fits and looks right. The
capstone is your finished gown.
What "done" means here. A 3–5 page responsive business website for Adaeze Fashion (or a business you choose),
containing:
a Home page (welcome/intro and a call to action),
a Shop/Products page (a grid of products with prices),
an About page (the business story and values),
a Contact page (a styled form, and a map from Session 10),
consistent navigation on every page,
a responsive layout,
images with meaningful alt text,
valid HTML and CSS,
tested on mobile and desktop.
Misconception. "The capstone must be perfect." No. The standard is competent and explainable. Minor issues that you can
identify and fix yourself are acceptable. A polished site you cannot explain is not passing.
Limitation and honesty. This course, and therefore this capstone, covers HTML and CSS only. That makes you an entry-level
front-end web designer — someone who can build a clean, responsive, static business website. It does not make you a full-
stack developer. We revisit this clearly in the wrap-up.
F.2 Milestone checkpoints — what should already be done before Session 12
Use this table at the start as a self-audit. Anything unticked is today's priority.
Checkpoint Introduced in Should be complete by
Business chosen; site plan and wireframes sketched Session 7 Before Session 8
3-page HTML structure: header, nav, main, footer; pages linked Session 8 Before Session 9
Shared stylesheet linked to every page; palette, type scale, spacing Session 9 Before Session 10
Responsive (tablet + mobile media queries) Sessions 6 & 9 Before Session 10
CSS interactivity: hovers, transitions, a reveal; map and video embeds; favicon Session 10 Before Session 11
Site tested: links, images, form, responsive, validators, accessibility Session 11 Before Session 12
All pages present (3–5); project folder organised Sessions 7–11 Entering Session 12
Corrected bugs logged; validation passing Session 11 Entering Session 12
Entering Session 12, the minimum baseline is: all pages built and styled, navigation working on every page, responsive, a
contact form, images with alt text, and the site having been tested at least once. Learners below this baseline should switch to
the Level 1 supported track (Section O) immediately.
F.3 Finalising the website — the last 10%
The difference between a good student site and a passing capstone is usually a short list of small, high-value items.
Structure and semantics (the skeleton must be right).
Every page starts with <!DOCTYPE html> and <html lang="en"> .
The <head> contains <meta charset="UTF-8"> , the viewport meta, a descriptive <title> and the stylesheet <link> .
Use semantic elements: <header> , <nav> , <main> , <section> , <article> , <footer> .
The same header/nav and footer appear on every page, with identical links.
Consistency (the brand must be one).
All pages use the same palette, fonts and spacing — ideally driven by :root variables.
One .button class reused everywhere.
Active nav link styled so the visitor knows which page they are on (optional but professional).
Responsiveness (it must work in a pocket).
Test at 375px (phone), 768px (tablet) and desktop.
No horizontal scrolling; cards become one column; header stacks; text does not overflow.
Content quality (it must read well).
Real, specific content — not "Lorem ipsum" and not "text here".
Correct Naira prices, a real Port Harcourt address and phone number.
No obvious spelling mistakes; headings in a sensible order (one <h1> per page).
The form (it must display properly).
Labels connected by for / id ; required fields; a clear :focus state; a styled submit button.
Honesty: the form displays and validates required fields, but HTML alone cannot send it. Sending requires a service (e.g.
Formspree, Netlify Forms) or a server. Do not claim it delivers email.
Code quality (it must be clean).
Indented, commented, organised files; a logical folder structure.
Validation and testing (it must be correct).
HTML and CSS pass the W3C validators.
Console free of red errors; every link and image works.
Accessibility (it must be usable by everyone).
Meaningful alt text; passing contrast (≥ 4.5:1 body text); visible focus outlines; labels.
Organised folder structure (the professional habit):
```text
adaeze-fashion/
├── index.html          (Home)
├── shop.html           (Products)
├── about.html
├── contact.html
├── css/
│   └── style.css
├── images/
│   ├── logo.png
│   ├── favicon.png
│   ├── hero.jpg
│   └── product-1.jpg ...
```
F.4 Publishing (optional but recommended — required for the certificate)
The CEA certificate requires a published website, so we attempt this where accounts and internet allow.
What "publishing" means. Right now your site lives only on your computer; the address in the browser bar starts with
file:///C:/... . Publishing copies your files to a web server so anyone can open them at a public https://... address.
Option A — GitHub Pages (free, recommended).
1. Create a free account at github.com (if you do not have one).
2. Click New repository; name it, e.g. adaeze-fashion ; make it Public; create it.
3. Upload your site files (drag-and-drop in the browser is fine for our small site): open index.html must sit at the top level,
not inside an extra folder.
4. Go to Settings → Pages; under Build and deployment, set Source to Deploy from a branch, branch main , folder / (root) ;
save.
5. Wait a minute or two. Your site appears at https://<your-username>.github.io/adaeze-fashion/ .
6. Open that URL, click through every page, and confirm the images load.
Option B — Netlify (free, drag-and-drop).
1. Create a free account at netlify.com.
2. On the dashboard, drag your whole project folder onto the "drag and drop to deploy" area.
3. Netlify gives you a public URL immediately (you can rename it in settings).
The single most common publishing bug: absolute paths. A path like C:\Users\Name\project\images\photo.jpg works only on
your machine. On the server it breaks. Always use relative paths ( images/photo.jpg ) so the site works everywhere. This is why
Session 11 tested for it.
Other publishing checks:
index.html must be the Home page (servers look for it by default).
File names are case-sensitive on servers ( Logo.PNG is not logo.png ). Match them exactly.
No spaces in file names; use hyphens ( product-1.jpg ).
Expected result: a public URL that opens your site on any device, with working pages, images, map and video.
Misconception. "Once published, it is finished." No — you can update files and the published site updates (GitHub Pages takes
a minute; Netlify is near-instant). Publishing is a step, not a finish line.
F.5 Preparing the presentation and viva
The presentation (3–4 minutes per learner). You are not reading your code aloud. You are showing a business owner what you
built and why.
A simple 4-part structure:
1. The business and the goal (30s): who Adaeze Fashion is and what the site must achieve.
2. The tour (90s): walk through Home → Shop → About → Contact, pointing out the navigation, the product grid, the
responsiveness (drag the window live), and the form.
3. The decisions (60s): two or three choices and why — the palette, the fonts, why grid for products, why the mobile
breakpoint.
4. The honesty (30s): one thing you are proud of, one thing you would improve, and what the site does not do (e.g. the form
does not send email without a service).
The viva. After (or during) your presentation, the instructor asks a few questions from the list in Section L. The viva exists to
make sure you understand your own work. Answer in plain English; if you do not know, say so honestly and reason aloud —
that is respected far more than a bluff.
Presentation tips for a Nigerian classroom:
Speak clearly and a little slower than usual.
Point at the screen so the audience follows.
If something breaks live, stay calm, open DevTools, and treat it as a real-world moment — explaining the fix is showing
competence.
Misconception. "The viva is a trap." It is the opposite: it is your chance to show that the work is yours and that you understand
it. A site you can explain is worth far more than one you cannot.
F.6 What comes after this course (introduction)
You are finishing the Web Design course. That is a real achievement and a real, marketable skill — but it is a foundation, not the
ceiling. Section N explains exactly what you are now qualified to do and what to learn next. For now: finish, present, and be
proud.
F.7 Summary of the session
The capstone is a 3–5 page responsive business website that draws together every skill.
Final polish focuses on structure, consistency, responsiveness, content, the form, code quality, validation and accessibility.
Publish (GitHub Pages or Netlify) using relative paths and a top-level index.html .
Present in four parts and answer the viva honestly.
You are an entry-level front-end web designer (HTML/CSS) — not a full-stack developer. JavaScript and frameworks
come next.

## G. INSTRUCTOR DEMONSTRATION (12 minutes)
<!-- kind:demo -->
There is no new coding demonstration today. Instead, two short demonstrations set the learners up to succeed.
G.1 Demonstration 1 — the benchmark tour and self-audit (6 minutes)
Say: "Before you finish your own, let me show you exactly what I am looking for, using my reference site."
1. Open the instructor's Adaeze Fashion site in Chrome.
2. Walk through every page, pointing out each rubric item out loud:
semantic structure (view the Elements panel to show <header> , <nav> , <main> , <footer> );
the shared stylesheet and :root variables;
the product grid becoming one column when the window narrows (drag it live);
the styled form with a visible :focus ring and label for / id ;
the map and video from Session 10;
the favicon in the tab.
3. Inject a final "polish" bug on purpose: rename style.css in the reference to styles.css temporarily and refresh. The site
loses all styling.
Say: "Even at the final minute, one wrong character can break everything. That is why we re-test after every change —
right up to publishing." Restore it.
4. Open DevTools Console to show no red errors, then briefly show a passing W3C validation result.
5. Ask: "Which of these will you check on your own site in the next 15 minutes?" (Let learners call out items; this seeds their
self-audit.)
G.2 Demonstration 2 — publishing walkthrough (6 minutes)
Say: "A website on your laptop is a website nobody can visit. Watch how fast we put it online."
1. Open github.com, create (or open) a public repository named adaeze-fashion-demo .
2. Upload the instructor's files (drag-and-drop), making sure index.html is at the top level.
3. Go to Settings → Pages, set the branch to main and folder to / (root) , and save.
4. Wait, refresh the Pages section, and open the generated URL.
Expected: the live site appears at https://<username>.github.io/adaeze-fashion-demo/ .
5. Click through the pages; show the map and video loading over the internet.
6. Common trap to show: deliberately set an absolute image path in one page (e.g. C:\...\images\hero.jpg ), redeploy (or just
explain), and show the broken image on the live site. Say: "This is the number-one publishing mistake — always relative
paths."
Questions: "Why must index.html be at the top level?" (Servers look for it as the default home page.) "Why do relative paths
matter more online than offline?" (Absolutes point at your own computer, which the server does not have.)

## H. GUIDED PRACTICAL EXERCISE (18 minutes)
<!-- kind:guided_practical -->
Objective: A guided self-audit and final-polish clinic. Learners run the rubric against their own site, fix the highest-value gaps,
and prepare to present.
Starting materials: The learner's project, open in VS Code and Chrome; the printed rubric; internet for re-checking embeds and
validating.
Procedure (instructor walks the room continuously; learners work through the checklist, pausing for short group checks):
1. Structure audit (3 min). On each page, confirm <!DOCTYPE html> , <html lang="en"> , charset, viewport, title and the
stylesheet <link> . Fix any missing.
2. Consistency audit (2 min). Confirm header/nav and footer are identical on every page, and that every page links the same
style.css . Check that :root drives the colours.
3. Responsive audit (4 min). Press Ctrl+Shift+M ; check 375px, 768px, desktop. Pause and predict: "At 375px, is there any
horizontal scrollbar?" (There should not be.) Fix any overflow.
4. Content audit (2 min). Read each page aloud in your head. Fix spelling, replace placeholder text, confirm Naira prices and a
real Port Harcourt address.
5. Form audit (2 min). Click each field; confirm the label focuses the field, the :focus ring shows, and required fields are
enforced.
6. Code quality (1 min). Confirm files are indented and commented, and the folder structure matches Section F.3.
7. Validation (2 min). Validate one HTML page and the CSS. Fix the first error, re-validate, repeat. Expected: "No errors".
8. Accessibility (2 min). Check body-text contrast in DevTools; confirm every <img> has meaningful alt ; Tab through and
confirm a visible focus ring.
9. Presentation rehearsal (2 min with a partner). Give your 4-part pitch to a neighbour in 2 minutes; the neighbour asks one
viva question from Section L. Swap.

## J. Real-World Case Study
<!-- kind:case_study -->
Situation. Emmanuel finished the CEA Web Design course last term. Two weeks later, a friend opening a barbershop in Rumuola
asked him to build a simple website. Emmanuel sat down on a Saturday morning, reused his own capstone structure, swapped
the content and colours, tested it on his phone and his laptop, published it with GitHub Pages, and shared the link that
afternoon. His friend paid him, and the shop started getting booking messages from the site.
Relevant facts.
Emmanuel did not invent anything new; he reused a proven structure and adjusted it.
He tested on two devices and validated before publishing — so nothing was broken on launch.
He was honest that the contact form displayed but did not yet send email, and offered to add that later for a small fee.
Decision point. Why was Emmanuel able to deliver in one day when he had never charged for a website before?
Possible explanations.
1. He was born a "tech person".
2. He had practised the whole process repeatedly — plan, structure, style, responsive, test, publish — until it became a routine
he could repeat for any small business.
3. He got lucky.
Recommended answer. Explanation 2. The capstone is not a one-off exam; it is a rehearsal of a repeatable process. Because
Emmanuel had built the Adaeze Fashion site end-to-end, the second site was mostly substitution: new text, new photos, new
palette, same structure. That is exactly how entry-level freelance work begins.
Trade-offs.
Reusing a structure is fast and reliable, but he must still change the content, colours and images so no two clients look
identical.
Being honest about the form's limits protects his reputation and can lead to paid follow-up work.
Professional connection. Many real front-end jobs are adapting known patterns rather than inventing new ones. The
confidence to say "I can build you a clean, responsive 4-page website and publish it" — and to actually do it — is precisely what
this course certifies.

## L. Viva Question List with Model Answers
<!-- kind:knowledge_check -->
(Instructor asks 4–6 of these per learner. Learners may see the list beforehand so the viva is about understanding, not surprise.)
1. Why did you choose these colours and fonts? Model answer: "I chose three or four colours — a dark colour for the
header/footer, an accent for buttons, and a light background — so the site looks consistent. I used two fonts: one for headings
and one for body, so text stays readable. I stored the colours as variables in :root so I could change them in one place."
2. Walk me through the structure of one of your HTML pages. Model answer: "It starts with <!DOCTYPE html> and <html
lang='en'> . The <head> has the charset, viewport, title and stylesheet link. In the <body> I have a <header> with the logo and
<nav> , a <main> holding the page content in sections, and a <footer> . I used semantic elements so the code is clear and
accessible."
3. How did you link your pages and your stylesheet? Model answer: "Each page links the others through the <nav> using
relative paths like shop.html . Every page has one <link rel='stylesheet' href='css/style.css'> in the head, so all pages share the
same design and update together."
4. How does your site adapt to a phone? Model answer: "I used the viewport meta tag and media queries. Below 1023px the
product grid becomes two columns; below 767px it becomes one column and the header stacks. I tested it with the Chrome
device toolbar at 375px and 768px."
5. Show me how your stylesheet is organised. Model answer: "It goes in order: custom properties, reset and base, typography,
layout, header and nav, hero, buttons, product grid, forms, footer, then media queries at the bottom. Each section has a
comment header so it is easy to find things."
6. Why did you use grid for the products and flexbox for the header? Model answer: "The products need neat rows and
columns that line up, which grid does well with grid-template-columns: repeat(3, 1fr) . The header is a simple single row with
space between the logo and the nav, which is what flexbox is best at."
7. What does your contact form do when someone clicks 'Send'? Model answer (honest): "Right now it displays and will not
submit if a required field is empty, because of the required attribute. But HTML alone cannot send the message anywhere —
that needs a form service like Formspree or a server. I would add that as a paid next step."
8. What did you test, and what did you fix? Model answer: "I clicked every link, checked every image, opened the Console for
errors, tested the form, checked the site at phone and desktop widths, and ran the W3C validators. I fixed a wrong image file
name and a missing semicolon that was breaking a rule."
9. What is a relative path and why does it matter? Model answer: "A path relative to the current file, like images/hero.jpg ,
using forward slashes. Absolute paths like C:\\... only work on my computer, so the images break when I publish. Relative
paths work everywhere."
10. Tell me about one bug you found and how you found it. Model answer: "My product heading was not styled. I inspected it
in DevTools and saw the rule .prodcut h3 did not match my class product — a spelling mistake. I fixed the selector and it
worked."
11. Did your page pass validation? How do you know? Model answer: "Yes. I pasted each page into validator.w3.org and the
CSS into jigsaw.w3.org/css-validator, and both showed no errors. I fixed errors from the top down and re-validated."
12. What would you add next if you learned JavaScript? Model answer: "A working menu that opens and closes on click, real
form submission and validation, and maybe an image slider. Right now the menu uses a CSS checkbox trick, which is not ideal."
13. What are you most proud of, and what would you improve? Model answer: personal but specific — e.g. "I am proud that
the product grid is responsive and clean. I would improve the About page content and make the form actually send messages."
14. Why can't you call yourself a full-stack developer after this course? Model answer: "Because I have learned HTML and
CSS, which build and style the front of a website. Full-stack also needs JavaScript, a server, a database and deployment logic —
that is the next course."
Scoring the viva (5 marks): 5 = confident and accurate on all; 4 = strong with minor hesitation; 3 = correct on most; 2 = partial;
1 = cannot explain; 0 = no viva.

designer using HTML and CSS. It does not make you a full-stack developer.

Build a clean, responsive, multi-page business website with HTML and CSS.

Test, debug and validate a site, and publish it to free hosting.
Explain your technical decisions in plain English.

JavaScript — the language that adds real interactivity (menus, form sending, sliders).
Backend development, servers and databases.
Frameworks and libraries (React, Vue, etc.).
Advanced performance, security or SEO.
