# HTML Intermediate

## A. Session Identification
<!-- kind:identification -->
**Week / module:** Week 1 — Module 1: HTML Foundations

**Recommended duration:** 105 minutes

**Difficulty:** Beginner

**Prerequisite knowledge:** Sessions 1–2. The learner can write a valid HTML document with headings, paragraphs, lists, emphasis and comments. Connection to previous session Session 2 gave us text structure. This session adds the elements that make a page a real website: links to move between pages, images to show the products, tables for price lists, semantic elements that describe the parts of a page, and a first look at forms.

**Preparation before class:** Academy PCs on; VS Code and Chrome open; webdesign-practice open; at least one image placed in webdesign-practice/images/ (for example product1.jpg or logo.png ); a second HTML file about.html available for the link demo; projector connected. Running project Adaeze Fashion grows from a single page into a small multi-page site. We add navigation links to about.html and contact.html , a price-list table, semantic structure, and the beginnings of a contact form (finished in a later session).

## B. Learning Outcomes
<!-- kind:outcomes -->
By the end of this session, the learner will be able to:
1. Create hyperlinks with the <a> tag and the href attribute.
2. Distinguish between an internal link (to another page on the same site) and an external link (to another website).
3. Open a link in a new tab using target="_blank" , and explain when this is appropriate.
4. Link to a section of the same page using an id and a # link.
5. Add images with <img> , correct src paths and meaningful alt text, and explain why alt is required.
6. Build a simple table with <table> , <tr> , <th> and <td> , and explain when a table is the correct tool.
7. Use semantic elements <header> , <nav> , <main> , <section> , <article> , <aside> and <footer> to describe the parts of a
page.
8. Explain the difference between a generic <div> and semantic elements, and when a <div> is acceptable.
9. Describe the parts of a form — <form> , <label> , <input> , <textarea> , <select> , <button> — and name several input
types.

"A Website You Cannot Navigation" (The Newspaper Analogy)
Instructor setup. Have the home page from Session 2 open in Chrome. It has headings, paragraphs and lists — but no links
and no images.
What the instructor says:
"Look at our Adaeze Fashion page. Is it a website yet? … It has text. But can a customer click anything? Can they go to an
About page? Can they see a single photo of Adaeze's beautiful gowns? No.
A page with only text is like a newspaper with no pictures and no page numbers — you can read it, but you cannot

- Hold up a newspaper if available, or draw a simple page layout on the board: a title at the top, a row of section names,
articles in the middle, a small side column, and a footer at the bottom.]
"A newspaper is organised. It has a masthead (the newspaper name), a menu of sections, articles, and a footer with

Expected learner response. Learners quickly see that a page without links or images is not a usable site. Some will say "we

F. FULL LECTURE NOTES (~40 minutes)
F.1 Links — the heart of the web
The idea. A hyperlink (or "link") is clickable text or an image that takes the user somewhere else — another page on the same
site, another website, or a place further down the same page. Links are what make the web a web.
Plain-English definition. A link is created with the anchor element, <a> , and the href attribute, which holds the destination.
Why they exist. Without links, every page would be an island. Links let a visitor move from Home to About to Contact, or jump
from a blog post to an external source, with one click.
Familiar analogy. A link is a door. The text between <a> and </a> is the door's label ("Enter the kitchen"); the href value is
where the door leads.
The basic syntax.
```text
<a href="about.html">About Us</a>
```
<a> — the anchor (link) element.
href — the attribute that holds the destination (think "hypertext reference").
"about.html" — the value: where the link goes.
About Us — the clickable text the user sees.
Expected result. The words About Us appear, usually in blue and underlined (the browser's default link style). Clicking them
opens about.html in the same tab.
F.2 Internal versus external links
Internal link — points to a page on the same website.
```text
<a href="about.html">About Us</a>
<a href="contact.html">Contact</a>
```
The value is a relative path (no https:// ), because the file lives in our own project folder.
External link — points to a page on another website.
```text
<a href="https://www.cea.ng">Cyber Elias Academy</a>
```
The value is a full web address, starting with https:// .
Why the difference matters. Internal links use relative paths so the whole site keeps working when moved to a server. External
links need the full address because they live on someone else's server.
Worked example — the Adaeze navigation.
```text
<nav>
  <a href="index.html">Home</a> |
  <a href="about.html">About</a> |
  <a href="contact.html">Contact</a>
</nav>
```
Expected result: three clickable words separated by | pipes; each opens its page in the same tab.
Misconception. "I must type the full address for my own pages too." No — for your own pages use the short relative path
( about.html ), not C:\... or a full web address.
F.3 Opening a link in a new tab
The idea. By default a link opens in the same tab. Adding target="_blank" opens it in a new tab instead.
```text
<a href="https://www.cea.ng" target="_blank">Visit Cyber Elias Academy</a>
```
When to use it. Usually for external links — so that when a visitor clicks a link to another site, your own site stays open behind
it. For your own internal pages, it is usually better to stay in the same tab.
A good habit (see the honesty note). Modern practice adds rel="noopener" alongside target="_blank" :
```text
<a href="https://www.cea.ng" target="_blank" rel="noopener">Visit Cyber Elias Academy</a>
```
rel="noopener" is a small security measure that stops the new page from being able to control your page. It is not visible to the
user but is good practice.
Misconception. " target="_blank" should be on every link." No — using it everywhere floods the user with tabs. Use it mainly for
external links.
F.4 Linking to a section of the same page
The idea. You can link to a specific part of a page using an id . This is common on long pages with a "table of contents" or
"back to top" link.
Step 1 — give the target element an id attribute (a unique name):
```text
<h2 id="services">Our Services</h2>
```
Step 2 — link to it with a # and the same name:
```text
<a href="#services">Go to Services</a>
```
Worked example.
```text
<a href="#contact">Jump to Contact</a>
```
```text
<h2>Our Services</h2>
<p>Custom gowns and uniforms.</p>
```
```text
<h2 id="contact">Contact Us</h2>
<p>Call 0800 000 0000.</p>
```
Expected result: clicking Jump to Contact scrolls the page down to the Contact Us heading.
Rules. An id must be unique on the page (only one element per id). Names have no spaces — use lowercase and hyphens
( #our-services ).
Misconception. " # links always go to the top." href="#" alone goes to the top of the page, but href="#contact" goes to the
element whose id="contact" . The name after # must match an id exactly.
F.5 Images — <img> , src and alt
The idea. The <img> element places a picture on the page. It is a void element — it has no closing tag and no content. Instead,
everything it needs comes from attributes.
```text
<img src="images/product1.jpg" alt="Adaeze Fashion Ankara gown in blue">
```
Line by line:
<img> — the image element.
src — the source: the file path of the image (here, inside the images folder — a relative path).
alt — the alternative text: a short description of the image.
Why alt is required.
1. Accessibility: screen readers read the alt text aloud to blind users, so they know what the image shows.
2. Broken images: if the image cannot load (wrong path, no internet), the browser shows the alt text instead of an empty
box.
3. Search engines: alt helps search engines understand the picture.
Good alt text. Describe the image's meaning briefly: alt="Ankara gown in blue with gold trim" . Bad alt text. alt="image"
(useless) or alt="gown.jpg" (that is the file name, not a description).
Image paths.
Relative: images/product1.jpg — the image is in the images folder of our project.
Absolute (external): https://www.example.com/photo.jpg — the image lives on another website.
Sizing note (for now). An image displays at its own size by default. We will control size and layout with CSS in later sessions; do
not use width/height attributes to fix big layout problems yet.
Worked example — a product on the Adaeze page.
```text
<h2>Featured Product</h2>
<img src="images/product1.jpg" alt="Adaeze Fashion blue Ankara gown">
<p>Our latest Ankara gown — perfect for weddings and celebrations.</p>
```
Expected result: the Featured Product heading, then the picture, then the caption. If the file is missing, the browser shows the
alt text "Adaeze Fashion blue Ankara gown" and a small broken-image icon.
Misconception. "If the image does not show, I forgot the <img> tag." Often the tag is correct but the path is wrong. Check src
character by character. (See K.2.)
F.6 Tables — rows, columns and cells
The idea. A table displays data in a grid of rows and columns. Use it for tabular data — price lists, timetables, comparisons —
where the rows and columns have meaning.
The tags.
<table> — the whole table.
<tr> — a table row (table row).
<th> — a table header cell (bold and centred by default; names the column).
<td> — a table data cell (the actual data).
Worked example — Adaeze's price list.
```text
<table>
  <tr>
    <th>Item</th>
    <th>Price</th>
  </tr>
  <tr>
    <td>Ankara gown</td>
    <td>₦25,000</td>
  </tr>
```
```text
  <tr>
    <td>Corporate uniform</td>
    <td>₦15,000</td>
  </tr>
  <tr>
    <td>Bridal wear</td>
    <td>₦80,000</td>
  </tr>
</table>
```
Expected result. A table with two columns. The first row (Item, Price) appears bold and centred (because those are <th> ). The
three data rows appear as normal cells.
Why not use tables for page layout. Long ago, people used tables to arrange a whole page (menus, columns). This is wrong
and outdated because tables do not adapt to phones and confuse screen readers. Today, layout is CSS's job; tables are for data.
Misconception. "Tables are for layout." No — tables are for tabular data. If you are laying out a page, use CSS (later sessions).
F.7 Semantic HTML — describing the parts of a page
The idea. Semantic means "carrying meaning". There are HTML elements that name the role of a part of the page, so the
browser, screen readers and search engines understand the structure.
The key semantic elements.
Element Meaning Where it goes
```text
<header>
```
The top of a page (or a section); usually the logo and main heading Top
```text
<nav>
```
A group of navigation links Usually inside the header
```text
<main>
```
The single main content of the page Middle
```text
<section>
```
A themed grouping of related content, usually with a heading Inside main
```text
<article>
```
Self-contained content that makes sense on its own (a blog post, a product) Inside main
```text
<aside>
```
Related but secondary content (a sidebar, opening hours) Beside or inside main
```text
<footer>
```
The bottom of a page; copyright and contact details Bottom
Why semantic HTML matters.
1. Accessibility: screen readers let users jump to the <nav> , <main> or <footer> , so blind users can skip around quickly.
2. SEO: search engines understand which content is important.
3. Maintainability: a developer reads <header> and instantly knows what it is; <div> says nothing.
4. Consistency: every page of a site uses the same pattern, so it is easy to keep consistent.
Worked example — the Adaeze Fashion page structure.
```text
<header>
  <h1>Adaeze Fashion</h1>
  <nav>
    <a href="index.html">Home</a>
    <a href="about.html">About</a>
    <a href="contact.html">Contact</a>
  </nav>
</header>
```
```text
<main>
  <section>
    <h2>Welcome</h2>
    <p>Custom clothing made in Port Harcourt.</p>
  </section>
```
```text
  <section>
    <h2>Our Services</h2>
    <ul>
      <li>Ankara gowns</li>
```
```text
      <li>Corporate uniforms</li>
    </ul>
  </section>
</main>
```
```text
<footer>
  <p>&copy; 2026 Adaeze Fashion. All rights reserved.</p>
</footer>
```
Expected result. The page looks much like plain text at first (these elements have little default styling), but the structure is now
meaningful. The &copy; code prints the copyright symbol ©.
Note on &copy; . &copy; is an HTML entity — a short code that prints a special character. It prints ©. We will meet a few
entities; they always start with & and end with ; .
Misconception. "Semantic tags change how the page looks." Mostly they do not — they describe meaning. Their value is for
accessibility, search engines and readability. Styling comes later with CSS.
F.8 <div> versus semantic elements
The idea. A <div> (short for "division") is a generic container with no meaning. It is useful for grouping things purely for
styling or layout, but it tells us nothing about what it contains.
The rule of thumb. Use a semantic element when one fits ( header , nav , main , section , article , aside , footer ). Use a
<div> only when no semantic element fits — usually as a styling wrapper for CSS.
Compare:
```text
<!-- Unclear: what is this? -->
<div>
  <h1>Adaeze Fashion</h1>
</div>
```
```text
<!-- Clear: this is the page header -->
<header>
  <h1>Adaeze Fashion</h1>
</header>
```
Why it matters. A page built entirely from <div> tags is like a storeroom where every box is labelled "stuff". A screen reader
cannot announce "navigation", and a future developer cannot tell regions apart.
Worked example — acceptable use of a <div> .
```text
<div class="hero">
  <h2>Custom clothing for every occasion</h2>
</div>
```
Here the <div> groups content that will later be styled as a "hero" banner (via the class ). It is a reasonable use because no
semantic tag describes a decorative banner.
Misconception. "Semantic tags are optional; <div> is simpler." For a small site they still matter: they make the page accessible
and easy to maintain, and they are expected in professional work.
F.9 Forms — an introduction
The idea. A form collects information from the user — a name, an email, a message. At the end of this course, the contact form
on Adaeze's Contact page is where customers will send enquiries.
Plain-English definition. A form is a group of input controls (fields) inside a <form> element, finished with a submit button.
The core tags.
Tag Purpose
```text
<form>
```
Wraps the whole form
Tag Purpose
```text
<label>
```

J. REAL-WORLD CASE STUDY — "The Inaccessible Government Page"
Situation. A public agency in Nigeria publishes a services page. The page looks fine on a normal screen, but blind users
complain they cannot use it. The developers used <div> tags for everything and used tables to arrange the whole layout.
Screen readers cannot tell where the navigation is, where the main content begins, or what the images show.
Relevant facts.
The page has a menu, a main article and a footer, but all are <div> s with no meaning.
Images have no alt text, so a screen reader says only "image".
The layout uses a giant layout table, so a screen reader reads the content in a confusing order.
The agency is legally and ethically expected to serve all citizens.
Decision point. How should the team fix the page so everyone can use it?
Possible approaches.
1. Leave it — most users have good eyesight.
2. Rebuild the page with semantic elements ( header , nav , main , article , footer ), add meaningful alt text to every
image, and stop using tables for layout.
3. Add a separate "text-only" version of the site, as was done in the 1990s.
Recommended solution (for this stage). Approach 2. The team:
replaces the top <div> with <header> and the menu <div> with <nav> ;
marks the main content with <main> and the article with <article> ;
wraps the bottom in <footer> ;
adds descriptive alt text to every meaningful image (and empty alt="" for purely decorative ones);
removes the layout table and lays the page out with CSS (learned later this course).
Trade-offs.
Approach 1 excludes a whole group of users and fails public-service expectations.
Approach 3 doubles the maintenance work and often gives disabled users a poorer, second-class experience — modern
best practice is one accessible site for everyone.
Approach 2 costs some rework now but gives one accessible, maintainable, professional site that also ranks better in search
engines.
Professional connection. Accessibility is a mark of professional web design and is increasingly a legal requirement for public
bodies. Real developers use semantic HTML and alt text as a matter of course. This is not "extra" work — it is part of doing the
job properly.
Transfer question for the class: "Why is semantic HTML important for a website that serves the public?" (Expected: screen-
reader users can navigate; the site is usable by everyone; search engines understand it; it is easier to maintain and legally sound.)

## K. Common Mistakes and Troubleshooting
<!-- kind:troubleshooting -->
K.1 A link goes to the wrong place or shows "not found"
Symptoms: Clicking a link shows a 404 or "file not found" page. Likely cause: A spelling mistake in the href , a wrong file
name, or a missing target file. How to investigate: Compare the href value, letter by letter, with the actual file name in the
Explorer. Corrective steps: Correct the spelling; make sure the target file really exists. How to confirm resolved: The link opens
the right page. Prevention: Use lowercase file names with no spaces; copy the exact file name into the href .
K.2 The image does not display (broken image icon)
Symptoms: A small broken-image icon and/or the alt text shows where the picture should be. Likely cause: The src path is
wrong, the file is in the wrong folder, or the file name/case is wrong. How to investigate: Check whether the image is really
inside the images/ folder and whether the path matches exactly (case matters on servers). Corrective steps: Fix the path, e.g.
images/product1.jpg , not product1.jpg or images\product1.jpg . How to confirm resolved: The picture appears. Prevention:
Always keep images in images/ and use forward slashes.
K.3 Label does not focus its input
Symptoms: Clicking the text label does nothing. Likely cause: The label's for does not match the input's id . How to
investigate: Compare for="..." with id="..." character by character. Corrective steps: Make them identical. How to
confirm resolved: Clicking the label moves the cursor into the field. Prevention: Write the input's id first, then copy it into
the label's for .
K.4 Table looks broken / columns misaligned
Symptoms: Cells jump into the wrong row or the table collapses. Likely cause: A missing or mis-ordered <tr> , <th> or <td>
tag, or a missing closing tag. How to investigate: Count the cells in each row; each row should have the same number of
<td> / <th> cells. Corrective steps: Add the missing cell or close the tag. How to confirm resolved: Rows and columns line
up. Prevention: Build one row fully, then duplicate it.
K.5 External link does nothing
Symptoms: Clicking an external link appears to do nothing. Likely cause: No internet connection, or a misspelled web address.
How to investigate: Check the Wi-Fi icon; check the href starts with https:// and is spelled correctly. Corrective steps:
Connect to the internet; fix the address. If offline, this is expected — internal links still work. How to confirm resolved: The
other site opens. Prevention: Test external links only when online; keep internal links relative.
K.6 Everything is built with <div>
Symptoms: No semantic elements used; future styling and accessibility suffer. Likely cause: Learner finds <div> familiar. How
to investigate: Count the semantic tags; there should be several on a full page. Corrective steps: Replace the top region with
<header> , the menu with <nav> , the content with <main> , sections with <section> , the bottom with <footer> . How to
confirm resolved: The page uses meaningful regions. Prevention: Start each page from a semantic skeleton.
Distinguish likely vs confirmed. Confirm before fixing: look at the actual error, the actual path, the actual for / id pair. Do not
guess.

## O. Instructor Evaluation Notes
<!-- kind:instructor_notes -->
Observable signs of genuine competence.
The learner creates correct internal and external links and explains the difference.
The learner adds an image with a correct relative path and meaningful alt text.
The learner chooses semantic elements over <div> and can say why.
The learner builds a table with a header row and aligned cells.
The learner matches every label for to its input id .
The learner tests links by clicking them rather than assuming they work.
Common misconceptions to watch for and correct.
"My own pages need the full https:// address." → Use relative paths for internal pages.
" alt is optional." → It is essential for accessibility and broken-image handling.
"Tables make good page layouts." → Tables are for data; layout is CSS's job.
" <div> is fine for everything." → Prefer semantic elements; use <div> only as a last resort.
"Submitting the form sends an email." → Not yet; a form needs a destination and a handler.
" target="_blank" on every link." → Mainly for external links.
Suggested remedial exercises.
1. Link repair drill: a page with three misspelled href s; the learner finds and fixes each.
2. Image path drill: give five src values, some correct and some wrong; the learner identifies the working ones and explains
why.
3. Semantic sorting: a plain-text layout description; the learner assigns header , nav , main , section , aside , footer to each
part.
4. Label/id matching: five labels and five inputs jumbled; the learner pairs them.
Differentiation.
Level 1 (supported): Provide a semantic skeleton file with the <header> , <nav> , <main> and <footer> already in place;
learners fill in the image, table and form fields. Pair with a confident learner.
Level 2 (standard): Complete the exercises and assignment as written.
Level 3 (challenge): Add a same-page table of contents using id / # links; add a second <img> inside a link (so the
image itself is clickable); add a checkbox and a radio group to the form, and a <fieldset> with a <legend> to group related
inputs.
Timing guidance (105 minutes). Opening 6 · Prerequisite 7 · Lecture 40 · Demonstration 15 · Guided practical 18 · Independent
exercise 15 · Case study 4 · Knowledge check 4 · Reflection/close 3. If slow, shorten the case study to 2 minutes and protect the
guided and independent practicals — building the linked pages is the priority. If fast, spend spare time on Level 3 tasks and peer
review of each other's site navigation.
