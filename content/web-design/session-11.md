# Testing and Debugging

## A. Session Identification
<!-- kind:identification -->
**Week / module:** Week 4 — Module: Publishing and Capstone

**Recommended duration:** 105 minutes

**Difficulty:** Beginner (builds on Sessions 1–10)

**Prerequisite knowledge:** Sessions 1–10. Learners can build and style a responsive multi-page site and add CSS interactivity and media.

**Connection to previous work:** In Session 10 the Adaeze Fashion site became lively — but lively is not the same as correct. A beautiful site with a broken link, a missing image or an easy-to-miss CSS typo still fails the customer. This session teaches the professional habit of testing before publishing: using Chrome DevTools, reading and fixing HTML/CSS errors, running the W3C validators, and checking accessibility and cross-browser basics.

**Preparation before class:** Academy PCs on; VS Code and Chrome; each learner's Session 10 project open; projector; a printed "Testing Checklist" and "Common Errors Reference" per learner; internet required for the W3C validators; a deliberately broken practice page (files in Section F.10) prepared and shared so every learner can debug a real broken page alongside the instructor.

## B. Learning Outcomes
<!-- kind:outcomes -->
By the end of this session, the learner will be able to:
1. Describe what testing and debugging mean and why a website must never be published untested.
2. Open and navigate Chrome DevTools — the Elements, Console and Network panels and the device toolbar.
3. Inspect an element and test CSS changes live in the Elements panel, then apply the confirmed fix to the source code.
4. Diagnose five categories of CSS mistake — a misspelled selector, a missing semicolon, a missing unit, a specificity
conflict and a wrong file path.
5. Check every link, image and page on desktop and on a simulated mobile width.
6. Check a contact form — labels, required fields, focus and layout.
7. Validate HTML and CSS using the W3C validators and interpret the results.
8. Run basic accessibility checks — colour contrast, alt text and form labels.
9. Perform basic cross-browser testing in at least two browsers.
10. Identify and fix a set of deliberate bugs in a provided broken page, and produce a short testing report.

## D. OPENING ACTIVITY (6 minutes)
<!-- kind:opening -->
Instructor setup: On the projector, open the deliberately broken practice page (Section F.10). It should look clearly wrong: an
unstyled block, a broken image icon, a link that goes nowhere, and a heading that is nearly invisible against its background. Do
not reveal any code yet.
What the instructor says:
"Nobody built this page on purpose to be broken — but every one of these problems is the kind of thing real designers
create by accident every single day: one missing letter, one missing semicolon, one wrong file name. On the surface it looks
like a disaster. In truth there are only a handful of small mistakes, and we can find every one of them in minutes.
Here is the secret: you do not fix bugs by staring and guessing. You fix them by investigating — using a tool that shows
you exactly what the browser thinks your code says. That tool is Chrome DevTools, and by the end of today you will use it
like a professional. Let us hunt these bugs together."
Expected learner response: Learners will point at the broken image or the invisible heading and volunteer guesses. Accept
guesses, then say: "Good instinct — but let us not guess. Let us prove it."
Why this opener works: It normalises mistakes (reducing shame and fear), makes the abstract idea of "debugging" concrete by
showing a real broken page, and immediately promises a tool that makes the task feel achievable rather than overwhelming.

## E. PREREQUISITE REVIEW (7 minutes)
<!-- kind:prereq_review -->
Fast oral round-robin. Questions on the projector.
Question 1: "Where should every page's stylesheet link go, and why does a page sometimes lose all its styling?"
Expected answer: in the <head> ; a missing or wrong href breaks all styling.
Common gap: learners check only one page. Remind them every page needs its own <link> .
Question 2: "What are the four layers of the box model?"
Expected answer: content, padding, border, margin.
Common gap: this matters today because missing units (e.g. padding: 20; ) is a common bug that silently breaks the box
model.
Question 3: "What does :hover do and where have we used it?"
Expected answer: styles a state while the mouse is over the element; used on nav links and buttons.
Common gap: confusing :hover with :focus ; remind them :focus is for keyboard and clicking into fields.
Question 4: "Why do all pages share one stylesheet, and what is a relative path?"
Expected answer: consistency and one-place updates; a path relative to the current file, using forward slashes.
Common gap: using backslashes; today this is a category of bug we test for.
Question 5: "Name one accessibility practice we applied last session."
Expected answer: visible focus outline, meaningful alt text, or sufficient contrast.
Common gap: none serious; this is a warm-up for the accessibility checks in Section F.7.
Bridge to today (say this):
"Every one of those answers is something that can break — and today we learn to catch it before a customer does. There is
a saying in our trade: 'If it works on your machine, you have tested nothing.' Today we test like the customer, on their
screen and their browser, and we fix what we find."
If more than a third of the class cannot answer Question 1, quickly re-demonstrate the <link> path on one page before
continuing.

## F. Full Lecture Notes
<!-- kind:lecture -->
F.1 What testing and debugging mean
The idea. Testing is checking that everything on the site works and looks right — links, images, pages, forms, layout and
accessibility. Debugging is finding and fixing the errors that testing reveals.
Plain-English definition. Testing is the check; debugging is the cure. They go together: you test to discover problems, then
debug to solve them.
Why they exist. A website is not "done" when it looks nice on your own screen. It is done when it works for a real customer on
a different device, a different browser and a flaky internet connection. Untested sites break in public — which costs the business
money and trust.
Analogy. Think of a tailor before a wedding. She does not hand over the aso-ebi because the fabric is beautiful; she checks the
seams, the hem, the fit — and fixes what is off before the customer wears it in public. Testing is the fitting; debugging is the
alteration.
What testing covers (our checklist today):
Do all links go to the right place?
Do all images load?
Does every page work, on desktop and on a phone width?
Does the form display and behave, with labels and required fields?
Is the page reasonably fast to load?
Does the code validate?
Is it accessible — contrast, alt text, labels?
Does it behave in more than one browser?
Misconception. "If it works, it is fine." Works on my machine is not the standard. The standard is works for the customer on their
device. This is why we simulate other devices and browsers deliberately.
Important limitation. No amount of testing proves a site is perfect; it reduces surprises. Even large companies ship bugs. The
professional habit is: test every time you change anything, not once at the end.
F.2 Chrome DevTools — your investigation toolkit
The idea. DevTools is a set of panels built into Chrome that shows you the live truth of what the browser loaded and how it
interpreted your code.
Why it exists. You cannot see the DOM, the computed styles, the loaded files or the errors just by looking at a rendered page.
DevTools exposes all of it.
How to open it: press F12 , or right-click any part of the page and choose Inspect, or press Ctrl + Shift + I . To open directly
on the Console: Ctrl + Shift + J .
The four panels we use today:
Panel What it shows Why we use it
Elements The live DOM (HTML) and every CSS rule that applies to the
selected element
Inspect structure; test CSS fixes live
Console Errors (in red), warnings (yellow) and any output Find broken paths, JavaScript errors,
missing files
Network Every file the page loaded, its size and status Find 404s (missing files) and heavy
images
Device toolbar A resizable viewport simulating phones/tablets Test responsive layout quickly
Two extra aids worth knowing:
Colour-picker contrast checker: in Elements, click any colour swatch to see the contrast ratio and whether it passes. Used
in Section F.7.
Lighthouse / Performance: a built-in audit for speed, accessibility and more. We only mention it today; deeper use is
beyond this course.
Analogy. DevTools is the mechanic's diagnostic computer plugged into the car. The car (page) may look fine parked outside,
but the computer shows exactly which sensor is failing. It does not fix the car for you — it tells you where to look.
Misconception. "DevTools changes are permanent." They are temporary: edits made in the panel last only until you refresh.
That is a feature — you can experiment freely, then copy the confirmed fix back into your real file. The panel is the experiment
bench; VS Code is the workshop.
F.3 Inspecting and testing CSS live in the Elements panel
The idea. Click an element on the page, and DevTools shows its HTML and the full list of CSS rules affecting it, with the winning
value highlighted.
The steps:
1. Press F12 to open DevTools.
2. Click the Elements tab.
3. Click the small arrow icon (top-left of the panel), then click any element on the page — or right-click the element and
choose Inspect. The element's HTML highlights in the DOM tree.
4. Below the HTML, the Styles pane lists every CSS rule that applies, in order, with the winning declaration shown at the top.
5. Tick/untick a checkbox to enable/disable a rule; click a value and type a new one to try a fix instantly.
6. When you find the fix, write it into your real style.css and save.
Reading the Styles pane (this is where debugging happens):
Struck-through declarations were overridden by something more specific. That is the visual sign of a specificity conflict.
A rule shown as greyed/with a warning is invalid (e.g., a missing unit) and was ignored.
The Computed tab shows the final values the browser actually used (e.g., the real pixel height).
Worked example: a heading looks blue but you expected brown.
1. Right-click the heading → Inspect.
2. In Styles, find a struck-through color: #2c1810; and an active color: blue; above it.
3. That active rule is more specific (or comes later). Untick it — the heading turns brown. Confirmed.
4. Fix the losing rule in your source (make the selector more specific, or remove the conflicting rule).
Expected result: you can point at any element and see exactly which rule decides its look — no guessing.
Misconception. Learners think the first rule in the file always wins. Cascading works by specificity and source order, not by
which rule you intended. DevTools settles the argument by showing the truth.
Limitation. DevTools edits do not save. If you refresh, you lose them — always transfer the fix to VS Code.
F.4 Reading HTML errors
HTML is forgiving: browsers often "fix" small mistakes silently and show something. That is dangerous because a mistake can
hide for a long time. Here are the ones to look for.
1. Unclosed tags.
```text
<!-- Wrong -->
<p>Welcome to Adaeze Fashion.
<!-- Right -->
<p>Welcome to Adaeze Fashion.</p>
```
A missing </p> can swallow the next elements into the paragraph, changing the layout.
2. Incorrect nesting (tags crossed like scissors).
```text
<!-- Wrong -->
<p>We <strong>love fashion</p></strong>
<!-- Right -->
<p>We <strong>love fashion</strong></p>
```
Open and close in the correct order — like brackets: last opened, first closed.
3. Missing alt on images.
```text
<!-- Wrong -->
<img src="images/workshop.jpg">
<!-- Right -->
<img src="images/workshop.jpg" alt="Adaeze's tailoring workshop in Port Harcourt">
```
alt carries the image's meaning for screen readers and shows if the image fails.
4. Wrong file path.
```text
<!-- Wrong: points to a file that does not exist -->
<img src="images/photo.png">
<!-- Right: matches the real file name -->
<img src="images/photo.jpg">
```
A file-name mismatch is one of the most common bugs; the image shows a broken icon.
5. Missing <!DOCTYPE html> .
```text
<!-- Right — always at the very top -->
<!DOCTYPE html>
<html lang="en">
```
Without it, browsers may switch to "quirks mode" and render oddly.
6. Missing essential <head> lines.
```text
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Adaeze Fashion | About</title>
</head>
```
No charset → ₦ and apostrophes can display wrongly. No viewport meta → the site will not scale properly on phones.
How to catch HTML errors quickly. The Console shows some (e.g., failed resources); the W3C validator (F.6) catches the rest,
including unclosed tags and wrong nesting. Also inspect in DevTools: the DOM tree shows how the browser actually interpreted
your markup, which often reveals a mis-nested tag.
Misconception. "The page shows, so the HTML is fine." Not necessarily. Browsers paper over errors; validators and the DOM
tree reveal them.
F.5 Reading CSS mistakes
A single wrong character can silently disable a whole rule. Learn to recognise these five.
1. Misspelled selector (a typo that targets nothing).
```text
/* HTML has class="product" ... */
.prodcut { width: 300px; }   /* Wrong: matches nothing */
.product { width: 300px; }   /* Right */
```
The rule looks fine but never fires. In DevTools the element simply has no styles from it. Confirm by comparing the class in the
HTML with the selector character by character.
2. Missing semicolon.
```text
/* Wrong */
.product {
  color: #2c1810
  padding: 16px;
}
/* Right */
.product {
  color: #2c1810;
  padding: 16px;
}
```
The missing semicolon often causes the next declaration to be ignored too.
3. Missing unit.
```text
/* Wrong — the browser cannot guess "20" of what */
padding: 20;
/* Right */
padding: 20px;
```
Lengths need a unit ( px , % , rem , em , vw ). The unitless 0 is the only exception ( margin: 0; is fine).
4. Specificity conflict.
```text
p        { color: #333333; }   /* any paragraph */
#about p { color: #cccccc; }   /* MORE specific — this one wins */
```
The second rule is more specific (an id beats a tag), so the text is light grey, not charcoal — even if you wanted it charcoal. In
DevTools the losing rule is struck-through. Fix it by making the winning rule what you want, or by increasing the specificity of
the rule you intend to win (usually by adding a class), not by piling on !important .
5. Wrong file path (for the stylesheet or a background image).
```text
<!-- Wrong -->
<link rel="stylesheet" href="css/styles.css">
<!-- Right -->
<link rel="stylesheet" href="css/style.css">
```
```text
/* Wrong: background image not found */
.hero { background-image: url(../images/hero.jpeg); }
/* Right */
.hero { background-image: url(../images/hero.jpg); }
```
A wrong stylesheet path = no styling at all; a wrong background path = a silently missing background, visible in the Console as
a 404.
How DevTools helps with all five:
Elements → Styles: struck-through = overridden (specificity); greyed/invalid = typo/unit; missing rule = selector typo.
Console: red net::ERR_FILE_NOT_FOUND = wrong path.
Network: a 404 status next to a file = wrong path.
Misconception. "If the CSS is in the file, it applies." No — invalid declarations are ignored, and selectors that match nothing do
nothing. Only the computed styles matter, and DevTools shows them.
F.6 The W3C validators
The idea. The W3C (World Wide Web Consortium) publishes free tools that check your code against the official standards and
report every error and warning.
Why they exist. Browsers are lenient; the validators are strict. Strict checking catches subtle problems (unclosed tags, duplicate
ids, invalid attribute values) before they bite across different browsers.
HTML validator — validator.w3.org:
1. Open the site.
2. Choose the "Validate by Direct Input" tab.
3. Paste your full HTML (from <!DOCTYPE html> to </html> ).
4. Click Check.
5. Read the results: it lists each error with a line number and a short explanation, then warnings.
CSS validator — jigsaw.w3.org/css-validator:
1. Open the site, choose "By direct input".
2. Paste your CSS.
3. Click Check and read the report.
How to use the results like a professional:
Fix errors from the top down and re-validate after each fix — one error can cause several later ones to disappear.
Read what each error means; do not just hunt for the line. The message tells you the rule.
Advance from errors to warnings, but a "clean" pass means no errors (warnings are advisory).
A missing alt might appear as an error or a warning depending on the checker — treat it as something to fix regardless.
Expected result: after fixing, the HTML validator shows "Document checking completed. No errors or warnings to show." and the
CSS validator shows "Congratulations! No Error Found."
Misconception. "Validation is optional polish." Most professionals treat valid, standards-compliant code as a baseline — it is
more predictable across browsers and easier for the next person to maintain.
Limitation. Validators check standards compliance, not design quality or whether the content is correct. A valid page can still be
ugly or have the wrong prices. Validation is necessary, not sufficient.
F.7 Accessibility checks
The idea. Check that the site is usable by people with different needs — low vision, colour blindness, keyboard-only use, or a
screen reader.
Why. It is both ethical and practical: accessible sites reach more customers and are easier for everyone.
Three checks we run today:
1. Colour contrast. Text must stand out from its background — at least 4.5:1 for normal text, 3:1 for large text.
In DevTools, inspect a text element, click its colour swatch, and read the contrast ratio.
Example of a failure: light grey #cfcfcf on cream #fdf7f9 — far too faint. Fix by darkening the text.
Failures are common with gold-on-cream and grey-on-white palettes.
2. alt text. Every meaningful image needs a description; decorative images use alt="" .
Quick audit: in the Elements panel, click through the images, or in VS Code search the HTML for alt= . Every <img> must
have one.
A screen reader reads the alt ; ask yourself "does this make sense read aloud on its own?"
3. Form labels. Every input needs a <label> connected by for / id , so a screen reader (and a tap on a small screen) knows
what the field is.
```text
<label for="email">Email Address</label>
<input type="email" id="email" name="email" required>
```
The for="email" must match the input's id="email" . If it does not match, the label is not connected — a common, quiet bug.
Bonus check — keyboard only: press Tab repeatedly. You should be able to reach every link, button and field, and always see
where you are (the :focus-visible outline from Session 10).
Expected result: every image described, every field labelled and focusable, and all body text passing 4.5:1.
Misconception. "Accessibility is only for a few users." Poor contrast, tiny targets and missing labels frustrate everyone on a
bright phone screen or a rushed day.
F.8 Cross-browser basics
The idea. Different browsers occasionally render the same code slightly differently. Test in at least two so you are not surprised
when a customer opens your site in Firefox or Edge.
Why. Chrome is the most-used browser, but not the only one. A site that only works in Chrome fails the customers using
something else.
What to do:
1. Test the site in Chrome (primary), then in Firefox and/or Edge (on Windows, Edge is built in).
2. Look for: missing styles, shifted layout, fonts looking different, broken spacing, or an embed that will not load.
3. Note any difference and decide whether it matters.
Typical difference to watch for (from our lessons):
aspect-ratio is well supported in current browsers but was not in much older ones — this is exactly why Session 10 also
taught the padding-bottom fallback.
Some CSS features need vendor prefixes (like -webkit- ) in older browsers; for the simple CSS on this course, modern
Chrome/Firefox/Edge agree closely.
Expected result: the site looks essentially the same in Chrome and at least one other browser.
Misconception. "If it works in Chrome, it works everywhere." Not guaranteed. Testing is how you find out. If you only have
Chrome, at least use the DevTools device toolbar (which simulates different devices, though not other browsers' engines).
Limitation. You cannot test every browser and old version by hand. Real teams use automated services; for this course, two
modern browsers is a professional and realistic standard.
F.9 Loading speed basics
The idea. A page that loads slowly loses visitors. You do not need to be an expert; you need a few basic checks.
Why. Many customers in Port Harcourt browse on mobile data. Heavy pages are expensive for them and slow to open, so they
leave.
The basic checks:
1. Image file sizes. Open DevTools → Network tab, refresh, and look at the sizes. A single photo above roughly 300–500 KB
is usually too heavy for a gallery image. Fix by resizing images to the size you actually display, and compressing them.
2. File formats. Use JPG for photos, PNG for graphics needing transparency, and modern formats like WebP when available.
3. Lazy loading. Off-screen images should use loading="lazy" (added in Session 10).
4. Fewer, smaller files load faster than many large ones. Remove unused images and duplicate stylesheets.
Expected result: image sizes in the Network tab are sensible; the page opens in a second or two on a normal connection.
Misconception. "A bigger, higher-resolution image always looks better." On a web page the opposite is often true: an images
resized to the display size looks identical but loads far faster.
Limitation. This is a taste of performance work, not a full performance course. Tools like Lighthouse give deeper reports; we
only point the way today.

## J. Real-World Case Study

Situation. Ngozi runs a small online store selling shoes from Port Harcourt. She launched her website in a hurry and shared the

## K. Common Mistakes and Troubleshooting
<!-- kind:troubleshooting -->
Use this as the live guide. When a learner hits a problem, point them at the relevant row before answering.
K.1 A page has no styling
Symptoms: Plain black text, blue underlined links. Likely cause: Missing or wrong <link> href , or the file was renamed.
Investigate: Console → red net::ERR_FILE_NOT_FOUND . Fix: Correct the path/name in every page's <head> . Confirm: Styling
returns; no red error.
K.2 A whole CSS rule is ignored
Symptoms: Some properties work, one or two do not. Likely causes: Missing semicolon on the previous line; missing unit; a
missing { or } . Investigate: DevTools → the declaration is greyed/invalid; the CSS validator flags it. Fix: Add the
semicolon/unit/brace. Confirm: The property applies after refresh; validator passes.
K.3 A style does not “win”
Symptoms: You set a colour but another rule overrides it. Likely cause: Specificity conflict — a more specific selector (e.g. an id)
or a later rule wins. Investigate: DevTools → the losing declaration is struck through. Fix: Adjust the winning rule or make your
intended rule more specific (e.g. add a class); avoid !important . Confirm: Your value now appears un-struck.
K.4 An image is broken
Symptoms: Broken-image icon in place of the photo. Likely cause: Wrong file name or path; file not uploaded. Investigate:
Console/Network 404 naming the file; compare spelling and folder. Fix: Correct the path; ensure the file exists in the folder.
Confirm: The image displays; no 404.
K.5 The validator shows dozens of errors
Symptoms: An overwhelming list. Likely cause: One early error cascading into many. Investigate: Read the first two or three
errors only. Fix: Fix top-down, save, and re-validate between fixes. Confirm: The list shrinks quickly, then reaches zero.
K.6 A form label is not connected to its field
Symptoms: Clicking the label does nothing; screen readers announce an unlabelled field. Likely cause: The label's for does
not match the input's id . Investigate: Compare the two values character by character. Fix: Make them identical, e.g.
for="email" ↔ id="email" . Confirm: Clicking the label focuses the field.
K.7 It looks fine on desktop but breaks on mobile
Symptoms: Overflow, overlapping text or cramped layout on a phone. Likely cause: Missing viewport meta, or missing mobile
media query. Investigate: DevTools device toolbar at 375px. Fix: Add the viewport meta and a max-width: 767px media query.
Confirm: The layout reflows cleanly at phone width.
Distinguish likely vs confirmed: Never fix on a hunch. Open the Console, inspect the element, or run the validator and see the
cause before editing. Confirming first is what separates a professional from a guesser.

INSTRUCTOR ANSWER KEY (Q1–Q7)
A1. Testing is checking that links, images, pages, the form, layout, accessibility and speed all work; debugging is finding and
fixing the errors that testing reveals. A2. (b) Console and Network (the Console shows the error; the Network panel shows the
404). A3. They are temporary because the panel edits the live page in memory, not the saved file. This is useful because you can
experiment freely, confirm which fix works, and only then write it into style.css — you can break nothing permanently. A4. (a)
misspelled selector (targets nothing); (b) missing unit (should be 20px ); (c) missing semicolon after #333 ; (d) contrast failure
(too light) — darken it. A5. The declaration appears struck through in the Styles pane. The professional fix is to adjust the
winning rule or increase the specificity of the rule you intend to win (usually by adding/using a class) — not to use !important .
A6. (1) Check the Console for a red net::ERR_FILE_NOT_FOUND on the stylesheet — confirms a wrong path. (2) Compare the href
in the <head> with the real file name and folder. (3) Confirm the file is saved and the <link> exists on that page. A7. Colour
contrast (≥ 4.5:1 for normal text), meaningful alt text on images, and form labels connected by for / id (plus
keyboard/focus testing).

## N. Reflection and Recap
<!-- kind:reflection -->
Plain-English summary. Today you became a tester and a detective. You learned that "it works on my machine" is not the
standard; the standard is "it works for the customer". You used Chrome DevTools — the Console, Network, Elements and device
toolbar — to see what the browser really did, inspected elements to test CSS fixes live (remembering that panel edits are
temporary), and learned to diagnose misspelled selectors, missing semicolons, missing units, specificity conflicts and wrong file
paths. You ran the W3C HTML and CSS validators, checked contrast, alt text and labels, tested in a second browser, and looked
at image sizes for speed. Most importantly, you debugged a genuinely broken page by confirming each cause before fixing it.
Five important takeaways:
1. Test like the customer — every page, every screen size, more than one browser.
2. Investigate before fixing: the Console, Styles pane and validators reveal the true cause.
3. DevTools edits are temporary; the permanent fix goes in your source file.
4. Fix validator errors top-down and re-validate after each fix.
5. Accessibility — contrast, alt , labels, focus — is part of testing, not an afterthought.
Questions to help you recognise what you can now do:
Can I find a broken image or link using DevTools without guessing?
Can I tell when a CSS rule is being ignored or overridden, and why?
Can I get my HTML and CSS to pass the W3C validators?

## O. Instructor Evaluation Notes
<!-- kind:instructor_notes -->
Observable signs of genuine competence:
Learner opens DevTools unaided and reads the Console error text rather than guessing.
Learner inspects an element and correctly identifies a struck-through (overridden) rule.
Learner confirms a cause before fixing ("the Console says the file name is wrong").
Learner fixes validator errors top-down and re-validates.
Learner checks mobile width with the device toolbar and catches overflow.
Learner tests at least a second browser and reports a real observation.
Learner treats accessibility (contrast, alt , labels) as part of testing.
Common misconceptions to watch for and correct:
"It works on my machine, so it works." → Test like the customer on other sizes and browsers.
"DevTools saved my change." → Panel edits vanish on refresh; copy the fix to your file.
"The validator is just for experts." → It is a basic professional habit.
"Solving specificity means adding !important ." → Fix the rule or its specificity instead.
"Accessibility is extra." → It is part of quality, and it helps everyone.
Suggested remedial exercises for learners who struggle:
1. Console reading drill: give five pages, each with one wrong path, and ask learners to name the missing file from the
Console alone.
2. Struck-through hunt: provide a page with three specificity conflicts and ask learners to identify each losing rule in the
Styles pane and fix it without !important .
3. Validator top-down drill: hand a page with one early error that causes five later ones; ask learners to fix only the first and re-
validate to watch the list collapse.
Differentiation:
Level 1 (supported): Provide the bug-hunt page with a written list of categories (not exact locations) to find, and walk the
learner through DevTools step by step.
Level 2 (standard): The exercise and assignment as written.
Level 3 (challenge): Use Lighthouse in DevTools to run an accessibility/performance audit, fix the top three items it reports,
and test in Firefox and Edge documenting any genuine differences.
Timing guidance: The DevTools investigation is the heart of the session — protect it. If the room is slow, run only the HTML
validator live and assign the CSS validation as homework. Internet failure is the main risk; if the validators are unreachable, teach
the Console/Elements work first and defer validation, since most of the learning is offline.
