# Building the Structure

## A. Session Identification
<!-- kind:identification -->
**Week / module:** Week 3 — Module 3: Building a Website

**Recommended duration:** 105 minutes

**Difficulty:** Beginner (comfortable with HTML from Sessions 1–3 and structure from Session 7)

**Prerequisite knowledge:** Sessions 1–7. The learner must be able to write a valid HTML page with headings, paragraphs, links, images, lists and semantic elements, and must have produced a website plan (sitemap, wireframes and content) in Session 7. If a learner has no plan, give them a printed copy of the instructor's plan at the start of class.

**Connection to previous work:** In Session 7 learners drew the blueprint for Adaeze's Fashion: the sitemap, wireframes, content and file structure. This session turns that blueprint into the real HTML skeleton — the five pages, their shared header and footer, and the content placeholders — ready to be styled in Session 9.

**Preparation before class:** Academy PCs on and logged in; VS Code and Chrome installed; the adaeze-fashion folder from Session 7 prepared on each machine (or created fresh this session); small placeholder images copied into images/ (or learners use simple coloured boxes); the projector set to show VS Code and Chrome side by side; print the "Multi-Page Website Checklist" (one per learner) and the "Adaeze's Fashion content sheet" (from Session 7).

## B. Learning Outcomes
<!-- kind:outcomes -->
By the end of this session, the learner will be able to:
1. Create multiple HTML files for a multi-page website using correct file names, including index.html for the Home page.
2. Build a consistent header and navigation (logo plus menu) that is identical on every page.
3. Build a consistent footer (copyright, contact details, social links) that is identical on every page.
4. Use semantic HTML elements — <header> , <nav> , <main> , <section> , <article> , <footer> — correctly across a real
project.
5. Link pages together using correct relative paths, and verify every link works.
6. Add images with descriptive alt text and correct relative image paths.
7. Build a contact form with proper <label> elements, input types and the required attribute (markup only — styling comes
in Session 9).
8. Organise the project folder so that HTML, CSS, images and JavaScript each live in the right place.
9. Explain why a consistent structure across pages matters for maintainability and user trust.

## D. OPENING ACTIVITY (6 minutes)
<!-- kind:opening -->
Instructor setup: On the projector, display the Adaeze's Fashion Home page wireframe from Session 7 beside an empty VS
Code window. Then, from a hidden tab, show the finished HTML skeleton (unstyled) of the same page — the header, hero text,
three product blocks and footer, with the browser's default plain look.
What the instructor says:
"Last session you drew this blueprint. Today we build the house. You may notice the finished structure looks plain — black
text on white, everything stacked. That is exactly right. Today we build the structure, the skeleton. Painting and decorating
come next session. If you skip the skeleton and try to make it pretty first, you will spend the whole day fighting a broken
structure.
By the end of today, you will have five real pages of the Adaeze's Fashion website — Home, Shop, Services, About and
Contact — all linked together, all sharing the same header and footer, all ready for CSS."
Expected learner response: Learners may be impatient that it looks "ugly". Reassure them: an unstyled but well-structured
page is a professional milestone; styling is quick once the structure is solid.
Then demonstrate the hook: In the projector browser, click the links in the starter page to move between Home, About, Shop
and Contact — showing that the same menu works everywhere. Say:
"Watch how the menu follows me to every page. That is the magic of a consistent structure. By the end of today, your own
menu will do this."
Why this opener works: It connects directly to the learner's own plan, frames "plain-looking" as intentional and professional,
and shows the payoff (working navigation) before the work begins.

## E. PREREQUISITE REVIEW (7 minutes)
<!-- kind:prereq_review -->
Run this as an oral round-robin. Put the six questions on the projector. Keep it quick — the practical work needs the time.
Question 1: "What are the five pages planned for Adaeze's Fashion?"
Expected answer: Home ( index.html ), About, Shop, Services, Contact.
Common gap: forgetting Services. Remind them it is optional but planned.
Question 2: "What file name must the Home page always have, and why?"
Expected answer: index.html , because web servers look for that name automatically.
Common gap: naming it home.html . Restate the reason.
Question 3: "Name the semantic elements we use for page structure, from top to bottom."
Expected answer: <header> , <nav> , <main> (with <section> / <article> ), <footer> .
Common gap: using <div> everywhere. Clarify: <div> is fine for wrapping, but semantic tags describe meaning.
Question 4: "What is a relative path? Give an example linking to the About page and to an image."
Expected answer: a path relative to the current file: href="about.html" and src="images/dress1.jpg" .
Common gap: full Windows paths. Remind them we never use C:\Users\... .
Question 5: "What attribute makes an image accessible when it cannot be seen?"
Expected answer: alt (alternative text).
Common gap: leaving alt empty or writing "image". Remind them it should describe the image.
Question 6: "Which folder holds the stylesheet, and which holds the photos?"
Expected answer: css/style.css and images/ .
Common gap: everything in the root. Remind them of the planned structure.
Bridge to today (say this):
"Your plan is the map. Today we follow it and build five pages that all share one header and one footer, and that link to
each other correctly. Consistency is the whole game: if the menu works on one page, it must work on all of them."
If more than a third of the class did not produce a Session 7 plan, hand out the instructor's plan and give a 3-minute recap of
the sitemap before continuing.

## F. Full Lecture Notes
<!-- kind:lecture -->
F.1 Creating multiple HTML files — one file per page
The idea. A multi-page website is simply several HTML files in the same folder, each representing one page.
Plain-English definition. Each page of the site is its own .html file. When a visitor clicks a link, the browser loads a different file
and shows it. There is no "one giant file" containing the whole website.
Why it exists. Splitting a site into separate files keeps each file small and manageable, lets several people work on different
pages, and lets the server send only the page the visitor asked for (faster loading).
The file names for our project:
Page File name Why this name
Home
```text
index.html
```
The default page a server shows first. Always this exact name.
About
```text
about.html
```
Lowercase, descriptive.
Shop
```text
shop.html
```
Lowercase, descriptive. (We do not call it products.html to match our menu label.)
Services
```text
services.html
```
Lowercase, descriptive.
Contact
```text
contact.html
```
Lowercase, descriptive.
Naming rules (repeated from Session 7 — they are that important):
1. All lowercase.
2. Hyphens instead of spaces.
3. Short and descriptive.
5. The Home page is always index.html .
Worked example — the same page shell used for every file. Every .html file begins with the same first block:
```text
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Adaeze's Fashion — Home</title>
  <link rel="stylesheet" href="css/style.css">
</head>
<body>
  <!-- header, main content and footer go here -->
</body>
</html>
```
Line by line:
<!DOCTYPE html> — tells the browser this is modern HTML5.
<html lang="en"> — the root element; lang="en" says the page is in English (helps screen readers and search engines).
<meta charset="UTF-8"> — lets the page show the ₦ symbol and other characters correctly.
<meta name="viewport" ...> — makes the page work on phones (Session 6).
<title> — the text shown on the browser tab; each page has its own title.
<link rel="stylesheet" href="css/style.css"> — connects the shared stylesheet (empty until Session 9).
<body> — everything the visitor sees.
Expected browser result: If you open any of these files now, you see a blank white page with the correct title in the browser
tab. That is correct — the content comes next.
Misconception. "I need a server to make multi-page files link." No. You can open index.html by double-clicking it, and links to
about.html will work locally.
Limitation. With separate files, if you change the header you must change it on every page. (There are ways to share it
automatically, but they need tools beyond this course. For five pages, we simply copy the shared blocks carefully.)
F.2 Building a consistent header and navigation
The idea. The header is the top of every page. It contains the site's identity (the logo or business name) and the navigation
(nav) — the menu that moves the visitor between pages.
Plain-English definition. The header is a shared bar at the top; the navigation is the set of links inside it. Because they are
identical on every page, the visitor always knows where they are and how to move around.
Why it exists. Consistency builds trust and reduces confusion. If the menu moved or changed on each page, visitors would get
lost and leave. A shared header is the single most important consistency feature of a multi-page site.
The header markup for Adaeze's Fashion:
```text
<header class="topbar">
  <a href="index.html" class="logo">Adaeze's Fashion</a>
  <nav>
    <ul>
      <li><a href="index.html">Home</a></li>
      <li><a href="shop.html">Shop</a></li>
      <li><a href="services.html">Services</a></li>
      <li><a href="about.html">About</a></li>
      <li><a href="contact.html">Contact</a></li>
    </ul>
  </nav>
</header>
```
Why each part is there:
<header> — the semantic container for the top area.
<a href="index.html" class="logo"> — the business name, wrapped in a link so clicking it always returns Home.
<nav> — the semantic container for navigation links.
<ul> and <li> — an unordered list is the standard, accessible way to mark up a menu (screen readers announce "list of 5
items", which helps users).
Each <a href="..."> — a relative link to another page's file.
Copy this block exactly onto every page. The only thing that changes from page to page is the <title> and the <main>
content — never the header.
Expected browser result (unstyled): A plain list of five links stacked vertically, with the business name above them: Adaeze's
Fashion, then Home, Shop, Services, About, Contact. It looks plain now, but in Session 9 the Flexbox CSS from Session 5 will turn
it into a purple bar with the logo on the left and the menu on the right.
Misconception. "Lists are only for bullet points of ordinary text." Lists are the correct markup for menus too, because a menu is
a list of links. Screen readers and search engines understand it better this way.
Limitation. The plain <ul> shows bullet points until CSS removes them. That is expected — styling is next session.
F.3 Building the main content — Home, Shop, About, Contact
The idea. The main content is the part of the page that is different on every page. It lives inside <main> .
Plain-English definition. <main> holds the unique content of this page (the reason the visitor came). By convention, a page has
exactly one <main> .
Why it exists. Marking the main content helps search engines and assistive technology skip straight to the important part of the
page, ignoring the repeated header and footer.
Home page main content:
```text
<main>
  <section class="hero">
    <h1>Custom Fashion for Every Occasion</h1>
    <p>Beautiful, affordable clothing, handmade in Port Harcourt.</p>
    <a href="shop.html" class="button">View Our Collection</a>
  </section>
```
```text
  <section class="featured">
    <h2>Featured Products</h2>
    <div class="grid">
      <article class="product">
        <img src="images/dress1.jpg" alt="Ankara dress in bright colours">
        <h3>Ankara Dress</h3>
        <p class="price">₦18,500</p>
      </article>
      <article class="product">
        <img src="images/dress2.jpg" alt="Lace gown with long sleeves">
        <h3>Lace Gown</h3>
        <p class="price">₦32,000</p>
      </article>
      <article class="product">
        <img src="images/dress3.jpg" alt="Aso ebi set in matching fabric">
        <h3>Aso Ebi Set</h3>
        <p class="price">₦27,500</p>
      </article>
    </div>
  </section>
</main>
```
Line by line:
<section> groups related content; each section usually has its own heading.
The .hero section is the big welcome banner.
<h1> is the main page heading — use one <h1> per page.
The .button link points to the Shop page — a call to action.
.featured lists three products.
Each product is an <article class="product"> — an independent, self-contained piece of content (a card).
<img> has a relative src and a meaningful alt .
.price shows the naira amount.
Shop page main content:
```text
<main>
  <section class="page-head">
    <h1>Our Collection</h1>
  </section>
```
```text
  <section class="shop">
    <div class="grid">
      <article class="product">
        <img src="images/dress1.jpg" alt="Ankara dress in bright colours">
        <h3>Ankara Dress</h3>
        <p class="price">₦18,500</p>
      </article>
      <!-- ...five more product articles... -->
    </div>
    <p class="order-note">To order, call 0801 234 5678 or use our contact form.</p>
  </section>
</main>
```
Expected browser result (unstyled): The heading Our Collection, then six product blocks stacked vertically (each with its
image, name and price), and finally the order note. In Session 9, this becomes a responsive grid.
About page main content:
```text
<main>
  <section class="about">
    <h1>Our Story</h1>
    <img src="images/about.jpg" alt="Adaeze at her sewing machine in the workshop">
    <p>Adaeze Okafor started Adaeze's Fashion with a single sewing machine in 2019.
       What began as a hobby soon grew into a trusted name in Port Harcourt.</p>
    <p>Today the workshop creates Ankara dresses, lace gowns, aso ebi sets and office
       wear for customers across Rivers State — all sewn by hand, with care.</p>
```
```text
    <h2>What We Value</h2>
    <ul>
      <li><strong>Quality</strong> — every stitch is checked before it leaves our shop.</li>
      <li><strong>Affordability</strong> — beautiful clothing that fits a real budget.</li>
      <li><strong>Style</strong> — modern designs that celebrate Nigerian fabrics.</li>
    </ul>
  </section>
</main>
```
Expected browser result (unstyled): The story heading, the workshop photo, two paragraphs, then a sub-heading What We
Value with a bulleted list. (This is the same Values content from Session 6's exercise, now in real HTML.)
Contact page main content (with the form):
```text
<main>
  <section class="contact">
    <h1>Get in Touch</h1>
```
```text
    <form action="#" method="post">
      <label for="name">Your Name</label>
      <input type="text" id="name" name="name" required>
```
```text
      <label for="email">Email Address</label>
      <input type="email" id="email" name="email" required>
```
```text
      <label for="message">Message</label>
      <textarea id="message" name="message" rows="5" required></textarea>
```
```text
      <button type="submit">Send Message</button>
    </form>
```
```text
    <div class="contact-info">
      <h2>Visit or Call Us</h2>
      <p>Aba Road, Port Harcourt, Rivers State</p>
      <p>Phone: 0801 234 5678</p>
```
```text
      <p>Instagram: @adaezefashion</p>
    </div>
  </section>
</main>
```
Line by line:
<form action="#" method="post"> — a form that will later send to the given address; # is a placeholder for now.
<label for="name"> — a label connected to the input with the matching id="name" . Clicking the label focuses the input;
screen readers read it aloud. This is an accessibility requirement, not optional.
<input type="text" id="name" name="name" required> — a single-line text box. required means the browser will not submit the
form if it is empty.
<input type="email" ...> — the browser also checks that the text looks like an email address.
<textarea rows="5"> — a multi-line message box.
<button type="submit"> — sends the form.
Expected browser result (unstyled): A simple form with each label on its own line above its input box, a large message box,
and a "Send Message" button. Crucially, if you click "Send Message" with the fields empty, the browser shows a small bubble
saying the field is required — that comes from the required attribute, with no CSS or JavaScript.
Why the form has no working "send" yet. Sending a form to an email needs a server or a form service. This session builds the
markup only. The point today is correct, accessible, semantic form structure. (Styles arrive in Session 9; interactivity in Session
10; understanding the limits honestly is part of being professional.)
Misconception. "The placeholder attribute can replace a <label> ." No. A placeholder disappears as soon as the user types, and
screen readers handle it inconsistently. Always use a real <label> . (You may also add a placeholder for users' convenience.)
Limitation. A basic HTML form cannot send email by itself. We are honest about this: the markup is correct, but a real working
form needs a service such as a form-handling tool or a server — beyond this course, though worth knowing.
F.4 Building the footer
The idea. The footer is the bar at the bottom of every page. It usually holds the copyright, contact details and social links.
Plain-English definition. A footer is a shared closing section, repeated on every page, giving the visitor quick access to essential
information.
Why it exists. Good footers put contact details on every page so a customer can reach the business without hunting. They also
carry the copyright notice and social links.
The footer markup for Adaeze's Fashion:
```text
<footer class="site-footer">
  <p>&copy; 2026 Adaeze's Fashion. All rights reserved.</p>
  <div class="social">
    <a href="https://instagram.com">Instagram</a>
    <a href="https://facebook.com">Facebook</a>
  </div>
  <p>Aba Road, Port Harcourt &middot; 0801 234 5678</p>
</footer>
```
Line by line:
<footer> — the semantic footer container.
&copy; — a special code that displays the © symbol.
.social — a group of external links (these are full URLs because they point outside our site).
&middot; — displays a small centred dot (·) between the address and phone.
Copy this exact footer onto every page, just before </body> .
Expected browser result (unstyled): Three lines at the bottom: the copyright, the two social links side by side, and the
address/phone. Plain now; styled later.
Misconception. "The footer is only for copyright." A footer is prime real estate: contact details, opening hours, social links and
quick links all belong there, on every page.
F.5 Linking pages together with relative paths
The idea. Pages are connected by <a href="..."> links, and the path inside href tells the browser where to find the other file.
Plain-English definition. A relative path describes where a file is relative to the file you are in. A link to about.html (no folder)
means "a file named about.html sitting beside me".
Why it exists. Relative paths keep the site portable: the same links work whether the files sit on your Desktop, on a USB stick, or
on a web server. Absolute paths like C:\Users\Adaeze\... break the moment the site moves.
The paths we use:
Link target href value Meaning
Another page in the same folder
```text
href="about.html"
```
A sibling file
An image in a subfolder
```text
src="images/dress1.jpg"
```
A file inside the images/ folder
The stylesheet in a subfolder
```text
href="css/style.css"
```
A file inside the css/ folder
An external website
```text
href="https://instagram.com"
```
A full URL (necessary because it is outside our site)
Worked example — link the menu to all pages:
```text
<nav>
  <ul>
    <li><a href="index.html">Home</a></li>
    <li><a href="shop.html">Shop</a></li>
    <li><a href="services.html">Services</a></li>
    <li><a href="about.html">About</a></li>
    <li><a href="contact.html">Contact</a></li>
  </ul>
</nav>
```
Expected browser result: From any page, clicking a menu link loads the matching page. Clicking the logo ( index.html ) always
returns Home.
The case-sensitivity trap. On Windows, About.html and about.html are the same file. On most web servers (Linux), they are
different files. If your HTML says href="About.html" but the file is about.html , the link works on your laptop and breaks online.
Always match the case exactly, and always use lowercase.
Misconception. "The file must be in the exact place the link says only on my computer." No — the structure on your computer
becomes the structure on the web. Get it right locally and it works everywhere.
Limitation. Relative links only find files that actually exist at that path. A typo in either the link or the file name produces a "file
not found" / 404. Always test every link (see Section K).
F.6 Images and alt text
The idea. Images are added with <img src="..." alt="..."> , and the alt text describes the image for people who cannot see it.
Plain-English definition. src is the path to the image file; alt is the alternative text shown if the image fails to load and read
aloud by screen readers.
Why it exists. alt text makes the site accessible to blind and low-vision users, helps if the image is slow or broken, and gives
search engines useful information. It is a basic professional and ethical requirement.
Rules for writing good alt text:
1. Describe what the image shows, briefly. Example: alt="Ankara dress in bright colours" , not alt="image1" .
2. Do not start with "Image of" or "Picture of" — screen readers already say it is an image.
3. If an image is purely decorative (adds no information), use alt="" (empty) so screen readers skip it.
4. Keep it short and useful.
Worked example:
```text
<img src="images/dress1.jpg" alt="Ankara dress in bright colours">
```
Expected browser result: The dress photo appears. If the file were missing, the browser would show the alt text "Ankara
dress in bright colours" in its place — proof that the alt text is doing its job.
Misconception. " alt is optional." It is effectively required for a professional site. Leaving it out harms accessibility and looks
careless.
F.7 Organising the project folder
The idea. Keep every file in its planned place.
Plain-English definition. The project folder (our root) contains the HTML files, the css/ folder, the images/ folder and the js/
folder.
The final structure this session produces:
```text
adaeze-fashion/
├── index.html
├── about.html
├── shop.html
├── services.html
├── contact.html
├── css/
│   └── style.css        (empty for now — written in Session 9)
├── images/
│   ├── logo.png
│   ├── hero.jpg
│   ├── dress1.jpg
│   ├── dress2.jpg
│   ├── dress3.jpg
│   └── about.jpg
└── js/

```
Why it matters at this stage: every href and src in your HTML points into this structure. If you put an image in the wrong
folder, the browser cannot find it, and you get a broken-image icon.
Expected result: In VS Code's Explorer panel, you can see all five HTML files in the root, with the css , images and js folders
below. You can find any file in two seconds.
Misconception. "The folder layout on my desktop does not matter as long as it opens." It matters because the links are relative
to it. A clean local structure equals a clean published structure.

## J. Real-World Case Study
<!-- kind:case_study -->
Situation. A small bakery in Port Harcourt, Sweet Crumb, hires a junior web designer to build its first site. On the Home page,
everything is perfect. But on the About page, the menu has a different colour, the footer is missing, and the "Order" link points
to a page that does not exist. On the Contact page, the form has no labels — just empty boxes — and older customers complain
they cannot tell what to type where.
Relevant facts.
The designer built each page by hand, from scratch, without reusing a consistent structure.
The header, menu and footer were typed differently on each page, so small differences crept in.
The form was copied from a random example online that used placeholders instead of labels.
Decision point. What single habit would have prevented almost every one of these problems?
Possible approaches.
1. Fix each page separately and hope no new differences appear.
2. Rebuild using a consistent structure: one header, one footer, copied identically onto every page, and proper labelled
forms.
3. Give up and use a website builder.
Recommended solution (for this stage). Approach 2. Consistency is the professional fix. Build one correct header and footer,
copy them exactly onto every page, link every page with correct relative paths, and use accessible labels on forms. This is
precisely the method taught today.
Trade-offs.
Approach 1 is whack-a-mole: fixing one page often introduces differences on another.
Approach 2 costs a little discipline up front and pays off for the life of the site.
Approach 3 abandons the skills the business paid for and reduces control.
Professional connection. Consistency and accessibility are two of the fastest ways a junior developer stands out. A site where
the menu, footer and forms behave the same on every page feels trustworthy. A site with a missing footer and unlabelled inputs
feels careless — and customers notice, even if they cannot name the problem.

## K. Common Mistakes and Troubleshooting
<!-- kind:troubleshooting -->
Use this table as the session's live troubleshooting guide. When a learner hits an issue, ask them to check the relevant row before
giving the answer.
K.1 A menu link says "file not found" (404)
Symptoms: Clicking a link shows a page that cannot be found. Likely causes: the href is misspelled; the case does not match
( About.html vs about.html ); the target file is in a different folder. How to investigate: Compare the href value with the exact
file name in VS Code's Explorer. Safe corrective steps: Correct the spelling and case; ensure the file is in the same folder (for
pages). How to confirm resolved: The link opens the correct page. How to prevent recurrence: Always use lowercase;
confirm files exist before linking.
K.2 Broken-image icon
Symptoms: A small broken-image icon appears where a photo should be. Likely causes: wrong src path; image in the wrong
folder; wrong file extension ( .png vs .jpg ). How to investigate: Check the exact file name and folder in Explorer; compare
with the src . Safe corrective steps: Fix the path to images/actualfilename.jpg . How to confirm resolved: The image shows
(or the alt text shows if the file is truly missing — then add the file).
K.3 The header or footer differs on one page
Symptoms: One page's menu or footer looks or reads differently. Likely cause: The page was typed separately instead of
copying the shared block. How to investigate: Compare the header block across pages. Safe corrective steps: Copy the
correct header/footer from a good page and paste it in, replacing the inconsistent one. How to confirm resolved: All pages
have an identical menu and footer.
K.4 Tags not closed
Symptoms: Content after a certain point looks wrong; the layout collapses. Likely cause: A missing closing tag such as </li> ,
</a> or </div> . How to investigate: Remember that browsers repair what they can; check the first line above where things
break. VS Code colour-coding helps — note where the colours change. Safe corrective steps: Close every element in the
correct order (last opened, first closed). How to confirm resolved: The structure renders as expected.
K.5 The form does not do anything when submitted
Symptoms: Clicking "Send Message" either does nothing or reloads the page. Likely cause: The form has no destination
action (it is # ), because sending requires a server or a form service. How to investigate: Check the <form action="..."> . Safe
corrective steps: For this course, this is expected. The markup is correct; connecting it to a real send service is beyond this
session. Confirm the required validation still works. How to confirm resolved: The browser blocks empty submissions
(validation works) and the labels are correctly connected.
K.6 Naira sign shows as ? or a box
Symptoms: ₦ appears as a strange symbol. Likely cause: The file was saved in a non-UTF-8 encoding. Safe corrective steps:
In VS Code bottom-right, click the encoding, choose Save with Encoding → UTF-8, and ensure <meta charset="UTF-8"> is in the
head. How to confirm resolved: The naira sign displays correctly.
K.7 Label does not focus its input
Symptoms: Clicking a form label does nothing. Likely cause: The label's for does not match the input's id . How to
investigate: Compare for="email" with id="email" . Safe corrective steps: Make them match exactly. How to confirm
resolved: Clicking the label places the cursor in the input.
Distinguish likely vs confirmed: In every case, confirm by checking the actual file names, paths and tag pairs rather than
guessing — VS Code's Explorer and colour-coding are your evidence.

## M. Knowledge Check
<!-- kind:knowledge_check -->
(Learner version — answers only in the Instructor Key.)
Q1. Short answer. What file name must the Home page have, and why?
Q2. Multiple choice. Which is the best alt text for a photo of a blue Ankara dress on the Shop page? a) alt="image" b)
alt="dress1.jpg" c) alt="Blue Ankara dress with short sleeves" d) (no alt attribute)
Q3. Explain in your own words. Why is it important that the header and footer are identical on every page?
Q4. Practical. Write the HTML for a navigation item that links to the About page ( about.html ), using the correct list markup.
Q5. Form markup. Write the two HTML lines that create a labelled input where clicking the label focuses the text box, for a field
named "email".
Q6. Semantic structure. Put these tags in the order they appear on a page: <main> , <footer> , <header> .
Q7. Error detection. This link works on the learner's Windows laptop but fails once the site is published. Why?
```text
<a href="Shop.html">Shop</a>
```
(Assume the file is actually named shop.html .)
INSTRUCTOR ANSWER KEY (Q1–Q7)
A1. index.html — because web servers are configured to show index.html by default when a visitor opens the site's main
address.
A2. (c) alt="Blue Ankara dress with short sleeves" — it describes the image clearly. "image" and the file name are not useful, and
omitting alt harms accessibility.
A3. Because consistency helps visitors always know where the menu is and how to reach the business; it builds trust. If the
header or footer changed between pages, users would feel lost, and the site would look unprofessional. It also makes the code
easier to maintain.
A4.
```text
<li><a href="about.html">About</a></li>
```
A5.
```text
<label for="email">Email Address</label>
<input type="email" id="email" name="email" required>
```
(The key point is that for="email" matches id="email" .)
A6. <header> , <main> , <footer> .
A7. Because the link uses a capital "S" ( Shop.html ) while the actual file is lowercase ( shop.html ). Windows is case-insensitive so
it works locally, but most web servers (Linux) are case-sensitive, so the link breaks online. Fix: use href="shop.html" .

Plain-English summary. Today you turned your Session 7 plan into real HTML. You created five pages — index.html , shop.html ,
services.html , about.html and contact.html — each with the same header, navigation and footer and its own unique content
inside <main> . You linked pages with correct relative paths, added images with meaningful alt text, built an accessible

Five important takeaways:
1. Home is always index.html ; each page is its own file.
2. The header, navigation and footer must be identical on every page.
3. Use relative paths ( about.html , images/dress1.jpg ) — never full Windows paths.

## O. Instructor Evaluation Notes
<!-- kind:instructor_notes -->
Observable signs of genuine competence:
The learner creates the header once and copies it accurately onto every page.
The learner uses lowercase file names and correct relative paths without reminders.
The learner writes meaningful alt text rather than "image1".
The learner connects every label to its input with matching for / id .
The learner clicks through every menu link and the logo to test before declaring finished.
The learner keeps one <h1> per page and uses <h2> / <h3> below it.
Common misconceptions to watch for and correct:
"The header can differ a little on each page." → It must be identical; copy, do not retype.
" alt text is optional." → It is a basic accessibility requirement.
"Placeholders can replace labels in forms." → Labels are required for accessibility; placeholders are optional extras.
"Capital letters in file names are fine." → They break on Linux servers; always use lowercase.
"The form should send email now." → Markup is correct, but sending needs a service beyond this session; required
validation still works.
Suggested remedial exercises for learners who struggle:
1. Link-hunt: give a site with three broken links and one broken image; ask the learner to find and fix each using the file
names.
2. Copy-the-header drill: give one correct header block and two pages with slightly different headers; ask the learner to make
them identical.
3. Form-pairing drill: give a form with unmatched for / id values and ask the learner to fix every pair so labels focus their
inputs.
Differentiation:
Level 1 (supported): provide index.html fully written and a partially written about.html ; the learner completes the About
page and creates the Gallery page.
Level 2 (standard): the practical and independent exercises as written.
Level 3 (challenge): add a gallery.html with eight images and a faq.html with a definition-style list; also add a <meta
name="description"> to each page's head and explain its purpose.
Timing guidance: The practical work is the priority — protect it. If the room is slow, reduce the demonstrated page count and
let learners finish contact.html at home, but ensure the shared header/footer consistency is done in class. If the room is fast, let
learners begin the Gallery extension live. The single most important thing to check before the session ends is that all five pages
link correctly — this is the foundation for styling next session.
